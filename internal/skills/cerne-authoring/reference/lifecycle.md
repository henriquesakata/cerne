## Feature loop

cerne mints the canonical `F-NNNN` id and gates each transition on a real document.

**Register at the start, not the end.** The first action when you pick up a task is step 1 below — run it *before* you start building, so the work is visible on the kanban (as a candidate) from minute one instead of an agent running in the dark. The spec/plan/result you write then carry it rightward across the board; if the work is dropped, `reject` it. Creating the feature is cheap and self-limiting — you only mint one when real work actually starts, so the board never fills with speculative ideas nobody is working on.

1. **Create** — `cerne feature new "<title>" --context "<1-3 sentences on why>" [--module <module>] [--facet <f>] [--component <c>] [--parent F-NNNN] [--fixes F-NNNN]` → candidate.
   - **Context is required at creation (F-0120):** a bare `feature new` is refused — a title-only candidate loses its creation context the moment the session that minted it is gone. The minimal path is `--context` (1-3 sentences of the *why*, seeded into the spec's Problem section (pt-BR: Problema)). Already have the full spec? `--file <spec.md>` (or piped stdin) births the candidate with the real spec committed and pushed, one-shot like `note new` — no fill, no push. `--file`/stdin and `--context` are mutually exclusive.
   - `--module` assigns the subsystem when the project declares modules; omit for cross-cutting work.
   - **Tag it (two axes, like notes/decisions/references):** `--facet` and `--component` (both repeatable, comma-separated). **facet** is the closed, validated set — `infra`, `code`, `data`, `process`, `auth` (D-0002/D-0003); an unknown facet is rejected with **no** write. **component** is open vocabulary, slug-normalized (`Gitback` → `gitback`). Filter the board with `cerne feature list --facet <f> --component <c>` — AND across axes, and AND with `--state`/`--module`/`--parent`. Tags fold into the FTS body (so `cerne search`/`ask` find a feature by a tag absent from its prose) and render on the feature's line (and as chips in the kanban/feature page). Re-tag in place — any state, rejected and superseded included; the body of a closed card still changes only by erratum — with `cerne feature retag F-NNNN --facet <f> --component <c>` (sets only the axis you pass; `--facet ""` clears it; never supersedes), so the implemented backlog can be categorized for retrieval too. Orthogonal to `--module` (product area) and `--parent` (epic decomposition).
   - `--capability C-0001,C-0002` (also on `epic new` and `task new`) links the card at birth, in the same single commit: every id is checked first, and an unknown or retired one creates nothing. Prefer it over a second `cerne feature capability` call.
   - `--parent F-NNNN` makes this feature decompose an epic. See **Epics**.
   - `--fixes F-NNNN` marks a correction of a delivered feature's defect (or `cerne feature set F-… --fixes F-NNNN` later; `""` clears). The process panel (`cerne stats --process`) counts it as an escaped defect when it is created within 28 days after F-NNNN's completion.
2. **Spec** — `cerne pull`, author `.docs/current/features/F-NNNN-<slug>/spec.md` (keep the `cerne_id` frontmatter), `cerne push`, then run `cerne feature approve F-NNNN --check` — it lists every impediment (spec still a stub, no valid `Bar:` line (pt-BR: `Barra:`), open clarifications, and the card's own: `untagged` — no facet nor component — and `capability-missing` — no capability while the project curates a taxonomy, F-0336), writes nothing and is open to agents — then fix every impediment it lists except open clarifications, which you leave for the human with the approve request (they are the human's questions — never answer them yourself). The card impediments are soft (the CLI approve refuses them, `--force` crosses, the UI does not) but they are yours: each comes with the `cerne feature retag`/`cerne feature capability` command that fixes it. Only then ask a human to run `cerne feature approve F-NNNN` (gate: a real spec, not the stub, naming its bar — and, by default, a human act; see **Human gates** below). Report the candidate is ready and wait. `feature new --file` and `feature spec` end with the same readiness in one line.
3. **Plan** — `cerne feature approve` scaffolds `plan.md` from a canonical template (or run `cerne plan draft F-NNNN`); fill it in, `cerne push`, then `cerne feature start F-NNNN` (gate: a real plan, not the stub).
   - **An approved spec stays editable (F-0318).** Fix it the normal way — `cerne pull`, edit `.docs/current/features/F-NNNN-<slug>/spec.md` and `cerne push` (the feature page editor and `cerne feature spec` write the same document) — no revert. The approve keeps the spec it accepted; any spec whose content differs from it, even by a comma, stales the approval (frontmatter, line endings and trailing whitespace do not count): the state stays `approved`, but `cerne feature start` refuses ("spec changed since approval") until a human re-approves with `cerne feature approve F-NNNN` on the approved feature itself — a human gate like the first approve; the human sees only the delta on the feature page. `cerne show` prints `approval: stale` and `cerne next` lists it under WAITING FOR RE-APPROVAL, never READY TO START (`approval_stale` in both `--json`; queue `awaiting_reapproval` in `next --json`), so check before picking up an approved feature. Editing back to the approved text clears it. Once in development, spec edits never stale anything. A feature approved before the approved version was recorded is never stale; a human `cerne feature approve F-NNNN` on it records the current spec as its baseline.
   - **Rewrote the spec? Update the plan and push it (F-0377).** Each plan write records the spec it was written against, so once the spec changes after it `cerne lint` warns `plan-older-than-spec` (approved or in development; advisory) and `cerne feature start` warns but proceeds — re-read the spec, update the plan (a line recording the re-check is enough) and push it (`cerne push`); pushing an unchanged plan sends nothing and clears nothing.
   - **An amendment goes into the text, never appended (F-0338).** When a criterion of an approved spec, or a task of the plan, changes for a reason worth keeping (a decision, the owner's go-ahead), rewrite that criterion or task in place and record it with `cerne feature amend F-NNNN --doc spec|plan --file <doc.md> --reason "<why>"` (approved or in development) — never appended at the end as an `## Emenda` section, which `cerne lint` warns as `appended-amendment`. The replaced text is kept as revision N, read with `cerne show F-NNNN --doc spec --rev N` (`--doc plan` for the plan), and `cerne show` lists the amendments under `## amendments`. Afterwards `cerne pull` refreshes `.docs/`. A spec amend stales the approval like any edit; the first text of a document goes in through `.docs/` + `cerne push`, not the amend. **In development the amend takes effect at once, with no re-approval** (no gate guards it), so the plan and the live children written against the previous text must be re-read. **The amend refuses a card another session is working on (F-0485):** active work of another session, or of another actor, on the card or on a live child refuses the spec or plan amend and writes nothing; the refusal lists each work (id, actor, session, last signal, title), what the amend causes in that state (an approved spec goes stale, in development it holds at once) and the plan and children written against the current text. Confirm with that session, then `--force` amends anyway and records `guard: forced` with the works' ids on the event. A work of your own actor with no session bound on this machine only warns; without `CERNE_SESSION` the decision falls to the actor, as in `cerne feature start`. The result amend has no such guard.
4. **Implement** — build it per your project's stack and conventions; add tests; review.
5. **Result** — `cerne feature start` scaffolds `result.md` from a canonical template (or run `cerne result draft F-NNNN`); fill it as you finish, `cerne push`, then `cerne feature complete F-NNNN` (gate: a real result, not the stub). This lands the feature on `implemented` ("Ready" on the kanban) — code done, awaiting human validation. Right after `cerne feature complete F-NNNN`, run `cerne cost F-NNNN --stamp` (before the human accept): it writes the `## Custo` block from the session transcripts into the result, and the epic rollup reads it. No manual "Done" status, no index edits — `cerne feature accept` (see below) is the only way to reach the actual `done` state.

**Waiting for a human gate (F-0460).** `cerne feature wait F-NNNN --for <state>` blocks until the feature reaches the state, or passes it on the forward path, then prints one line — the transition, who made it and when, and the next step — and exits 0. It refreshes the backend clone every `--interval` (30s; fetch + fast-forward, never a pull, so `.docs/` and `docs.lock` are untouched) and backs off on network errors. A stale approval (the spec changed after it, F-0318) is not approved until a human re-approves it. Exit 2: the state can no longer be reached (e.g. rejected while waiting for approved); exit 3: `--timeout` (24h; `0` checks once); exit 4: a channel message addressed to your session, not yet shown to it, arrived first (B-0065; one you already saw wakes you no more, B-0066) — the human's from the card's page, say — and it prints the message, how to answer it and the wait to run again. After asking for an approve or an accept, leave it running in the background when your harness wakes you as a background command ends; otherwise just stop. Without the wait the move still reaches you: a human's approve, accept, reject, revert or supersede leaves a card notice, the same line, that every session of this machine which worked on the card sees once, ahead of the channel, at its next turn or tool call (F-0504); a subagent leaves it to its session. The wait is what wakes a stopped session.

Terminal transitions when work is dropped or replaced: `cerne feature reject F-NNNN --reason "…"`; `cerne feature supersede F-NNNN --by F-MMMM --reason "…"`.

## Syncing when the backend may have advanced (parallel agents)

Reconciliation is **per document**, so disjoint edits never collide:

- **`cerne sync`** = pull (merge) + push, retrying transient advances — the one forward command when another agent/worktree may have changed the backend. Disjoint documents reconcile automatically, and so do edits to different lines of one document; edits to the **same lines** stop non-destructively (your version kept in `.docs/`, the remote version stashed under `.docs/.conflicts/`) and name the file with a diff. Fold in the remote changes you want, delete the stashed copy, then `cerne push`: push refuses the document while that copy exists (`cerne push --force` sends yours over the remote edit).
- **`cerne push`** auto-rebases per document: a remote advance on a *different* document never blocks it; only the same document changed both ways is a conflict.
- **`cerne pull`** 3-way merges: it brings in the remote advance while keeping your unsent `.docs/` edits, line by line when both sides changed the same document (it does **not** refuse on unsent edits). `--force` is only the explicit "discard my edits" escape — never the only way forward.
