## Epics (large work, decomposed)

An **epic is just a feature that has children** — the role is inferred from the parent link, there is no separate entity, so the epic gets the full feature lifecycle/spec/plan/result for free. Use one when a body of work is too large for a single spec and naturally splits into sub-features.

- Create a child under an epic: `cerne feature new "<title>" --context "<why>" --parent F-NNNN`.
- Link, move, or detach an existing feature later: `cerne feature reparent F-NNNN F-MMMM` (or `--clear`).
- **Epic ≠ module.** A module is the subsystem; an epic is decomposed work that may span modules. A feature can have both.
- **Read the breakdown, don't hand-maintain it:** `cerne status` shows an `ÉPICOS` section with `n/m` progress, and `.docs/CONTEXT.md` carries an *Épico* column plus a `## Épicos` section.
- The epic's lifecycle is independent (children completing does not auto-complete it). `cerne lint` flags inconsistencies — a live feature under a terminal epic, an epic completed with open children, or an epic still candidate/approved while a child is already in development (`epic-behind-children`: work started but the epic was never planned/started — write its plan and `cerne feature start` it).
- **Declaring intent upfront:** when a PRD is known from the start to decompose, `cerne epic new "<title>" --context "…"` mints a **declared** epic (`E-` prefix) instead of `feature new` — same lifecycle/gates, the prefix just signals the intent at birth (epic *behavior* is always structural: any feature with children). Decompose it with `cerne task new "<step>" --parent E-NNNN --context "…"` — a **task** (`T-` prefix) is a PRD execution unit already past its human gate: it is born `approved` (`cerne feature start T-NNNN` needs no plan of its own — the why lives in the parent PRD), but `cerne feature complete T-NNNN` still requires a real `result.md`. `--parent` on a task must name a committed feature/epic (approved or beyond).
- **Tasks inherit the parent's gates (T-0007).** An epic with N tasks costs two human acts, whatever N: the human's `cerne feature approve` on the parent approves along every candidate child the approve check passes (the others stay candidate, listed with the reason), and `cerne feature accept` on the parent accepts along every implemented task (an `F-` child keeps its own accept). Never ask the human for one accept per task. Each task still decides its **own bar** in its spec, in one of four forms: a named bar (its result records the round), `Bar: not applicable (…)` or `Bar: waived by human decision (…)` (no round), or `Bar: inherited from E-NNNN` (pt-BR: `Barra: não aplicável (…)`, `Barra: dispensada por decisão humana (…)`, `Barra: herdada de E-NNNN`), valid only on a task and only when the parent names a bar — no round in the task's result; the parent then owes the round in its own result. `cerne feature start T-NNNN` refuses a spec with no valid bar (a task has no approve, so the start is where the choice is charged), and a `padrão`/`avançado` task with `não aplicável` gets the `standard-without-bar` advice at `task new` and at start — advice, never a refusal. List the tasks' bars in the parent's spec, where the human's approve accepts them. A feature born with `feature new --parent` under a parent already approved is told that `cerne task new` is the path born approved.

**Bug route (a correction is not a feature, T-0006):** a defect report is a `B-` card — three fields (Context, Steps to reproduce, Expected × actual), the regression-test bar already filled, no plan.
- **A human reports a bug in the chat:** run `cerne bug new "<what breaks>" --context "<what happens, where>" --steps "<numbered steps>" --expected "<should happen × what happened>" --on-behalf "<their words, quoted>"` (add `--fixes F-NNNN` when it corrects a delivered feature: it inherits that card's facets, components and capabilities; `--steps` and `--expected` fill the other two sections; each omitted one keeps its template comment, and `--file report.md` replaces all three flags). The report is the approval: the card is born `approved`, so run `cerne feature start B-NNNN` without waiting for an approve. Write the regression test red first, fix, then `cerne feature complete B-NNNN` with a real `result.md`; accept stays human.
- **A bug you found yourself** (you found it yourself, the human did not ask): run the same command with `--origin agent` instead of `--on-behalf` (B-0086). It is born `candidate` with origin `agent`; ask a human to run `cerne feature approve B-NNNN` and stop — you do not approve your own demand.
- Never use `--on-behalf` for words the human did not say.
- **Who asked? Choose at every creation (B-0086).** In an agent shell, `feature new`, `bug new`, `epic new` and `task new` refuse, and write nothing, unless you pass exactly one of: `--on-behalf "<the human's literal words>"` (the human asked for this card; origin `human`) or `--origin agent` (the idea is yours; origin `agent`, and a bug stays `candidate` until a human approves). Both together are refused; a human in a terminal passes neither. A card born with the wrong origin is corrected by a human, in any state, with `cerne feature set <id> --origin human --on-behalf "<quote>"` (B-0085); an agent is refused.

**Housekeeping on a feature/epic in place (no lifecycle change):**

- `cerne feature rename F-NNNN "<new title>"` — allowed until development starts; frozen once implemented/terminal.
- `cerne feature spec F-NNNN --file <spec.md>` (or piped stdin) — replaces the whole spec of a **candidate** or an **approved** feature, same gated write the Backlog chat performs on confirmation; no state change, no retitle. On an approved feature a different spec stales the approval (F-0318, see **Plan** above). Refused past `approved`.
- `cerne feature set F-NNNN --owner <name> --priority p1` — sets owner and/or priority in place (only the flag passed changes; empty string clears); doesn't touch state, module, tags, or docs.
- `cerne feature revert F-NNNN --reason "…"` — one step back, a human act: undoes an approval (`approved` → `candidate`), sends a Ready card the human rejects or finds a bug in back to development (`implemented` → `in_development`), or undoes an acceptance (`done` → `implemented`). Documents and delivery links stay intact; an acceptance on merge that was reverted is not recorded again from the same PR (link a new one with `cerne feature deliver`).
- `cerne feature deliver F-NNNN --commit <sha-or-url> --mr <url>` — records the delivery commit/MR post-hoc, after the MR merges.
- `cerne feature mirror F-NNNN --title "<public title>" --summary "<public summary>" [--tracker <name>]` — **human only** (an agent is refused, like approve/accept): publishes the card as an issue on a tracker of `mirror.trackers` (default: the first) and links it; needs `mirror.enabled`. Only that public text, the card id and its state leave the backend, and the issue then follows the card's state on every transition. Never run it yourself: ask a human. `cerne mirror sync` imports each open issue no card or idea is linked to as an active idea (filtered by the tracker's `label`; promoting it hands the link to the card) and reapplies every mirrored card's state to its issue — the way back from a transition whose tracker round failed (the warning line names it). It exits 1 when a tracker or card warned.
- `cerne feature capability F-NNNN C-0001,C-0002` — links the feature to nodes in the product-capability taxonomy (`--clear` unlinks). The first argument takes a comma-separated batch of cards (`T-0019,T-0020 C-0001`, an epic's new tasks): one commit, aborted whole if any id is wrong. A new card takes `--capability` at birth instead. Manage the taxonomy itself with `cerne capability new "<name>" [--parent C-NNNN]`, browse it with `cerne capability list --tree`, retire a node with `cerne capability retire C-NNNN --reason "…"` (refuses with active children or linked features), or propose the whole tree from existing specs with `cerne capability bootstrap [--apply]`.
- `cerne next` caps each lint rule at 5 items under DEBTS (the rule header keeps its total, the rest is one `… and N more` line) and open pendings at 10; `cerne next --all` lifts both caps in the text, and `--json` is never capped. `cerne lint` always lists everything.
