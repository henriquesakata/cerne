## The Gauntlet protocol (F-0270/F-0271/F-0272): deliver against a real bar

The Gauntlet replaces self-scoring with a comparison against a real artifact that already exists — a delivery with no bar is graded against a rubric its own builder wrote, and that rubric always passes. Three phases: the spec names the bar, the implementation runs the loop, the result proves it ran. No project persona or instruction removes this protocol — only the project-wide light mode below, a choice the project makes in `.cernerc` and `cerne status` shows — and the loop's cost alone is not a reason to skip it on a change it pays for (see *When the tests suffice* below) — it runs once per delivery, not per commit, and collapsing roles to save a call is the one economy that voids the result. cerne holds the two ends mechanically (the Backlog analyst refuses to close a proposal with no bar; `cerne lint` charges the per-criterion evidence in `result.md`) — nothing watches the middle, so the loop's only gate is the record you leave and the human `accept` that reads it.

### Light mode (F-0364): a project without the Gauntlet

A project can run the spec → plan → result cycle without the Gauntlet by setting `[gates] gauntlet = "off"` in `.cernerc` — `cerne init` writes it for a new project, with an invitation to turn it on. The key is also the setting `gates.gauntlet` (values `on`/`off`): the owner flips it in the Settings screen of `cerne ui` or with `cerne settings set gates.gauntlet on|off --scope project`, and that command refuses an agent (`CERNE_ACTOR=agent`). Only the literal `"off"` counts: absent, `"on"` or any typo keeps the full protocol. In light mode `cerne feature approve` takes a spec with no `Barra:` line, `cerne feature complete` takes a result with no `## Gauntlet` section, and `cerne lint` stops charging `spec-missing-bar` and `result-missing-gauntlet`; the new spec scaffold asks for no bar. What stays: the per-criterion evidence (`result-missing-evidence` — the result still cites `critério N`), and the human `approve`/`accept` gates. The mode is visible, never silent — `cerne status` prints `Gauntlet: off (light mode)` and the dashboard shows it. Do not switch it yourself to get past a gate: turning the Gauntlet off is the project owner's decision, and the `.cernerc` diff shows it. To turn it on, use the Settings screen or `cerne settings set gates.gauntlet on --scope project`; everything below then applies. In an English project the same lines read `Bar:` and `criterion N`.

### Spec — name the bar, or record why there is none

A bar is a named reference plus how to reach it (URL, command, a file a critic can open), of the same class as what you are delivering: a prompt block against another prompt block, a lint rule against the strongest rule of the same package, an endpoint against another endpoint. Named without access is vague, and so is a category ("design bonito", "nível enterprise") — refuse a vague bar and ask for the named reference in its place, whoever offered it. You are the one it will be held against, so the weak-bar route is the tempting one: pick the strongest comparable artifact that already exists — preferably in this repo — and state in one clause why it is the strongest, so a critic can attack the choice. The bar you write is a proposal: put it in the spec's `Barra:` line yourself, with no acceptance round-trip first — the human's approve is its acceptance (the approve event records the accepted line, and the UI shows the bar next to the Approve button). Before asking for that approve, run `cerne feature approve F-NNNN --check` and fix every impediment it lists except open clarifications, which you leave for the human with the approve request; `cerne lint` also flags a candidate whose written spec has no valid bar as `spec-missing-bar`. A bar that is an external URL gets registered (`cerne reference new "<título>" --url <url> --informs F-NNNN`), or the spec is born with an `unregistered-source` debt. In a project documented in English the line is `Bar:`.

The spec's **Verification** section (**Verificação** in pt-BR) then carries exactly one of three literal forms, in the project's documentation language: they are written inside the spec, so a pt-BR project writes the Portuguese forms and an English project the English ones:

```
Barra: <referência nomeada + acesso>
Método: comparação cega, lado a lado, por crítico de contexto fresco que não participou da construção
Saída: vencer ou empatar; derrota abre nova rodada; parar perdendo só por encerramento humano registrado

Bar: <named reference + access>
Method: blind side-by-side comparison by a fresh-context critic that did not build it
Exit: win or tie; a loss opens a new round; stop losing only by a recorded human close
```

Filled in, the whole `<…>` gives way to the value — `Barra: modo spec do Kiro — kiro.dev/docs/specs; mesma classe: conduzir humano até spec completa`; a line that keeps the `<…>` is refused by the approve. In English: `Bar: Kiro's spec mode — kiro.dev/docs/specs; same class: leading a human to a complete spec`.

A named bar also needs its judge question: a `Pergunta ao juiz: <a pergunta que o juiz cego responde>` line right under `Saída:` (EN: `Question for the judge:`) is part of the bar's approval, and `cerne feature approve F-NNNN --check` lists `judge-question-missing` while it is absent. The two exemption forms below owe no question. In English the question goes right under `Exit:`.

— or the single line `Barra: não aplicável (<justificativa de 1 linha>) — padrão alternativo: <teste/benchmark/invariante>`, when the delivery has no comparable artifact (a point fix, pure backend with nothing observable): that classification is a proposal too, made in the open — the justification in the line, never a silent omission — and the human's approve confirms it; a human who disagrees does not approve. — or the single line `Barra: dispensada por decisão humana (<citação curta da fala que dispensou>)`, which exists only when a human refuses the bar on their own; you never suggest it, and the quoted words are what separate it from forgetting. A silent absence of a bar is never acceptable; a recorded exemption is. In English: `Bar: not applicable (<one-line justification>) — alternative standard: <test/benchmark/invariant>` and `Bar: waived by human decision (<short quote of the words that waived it>)`.

**When the tests suffice (F-0390).** A Gauntlet round costs about the same whatever the size of the change, so its share of a small change is larger. It pays on a change of behaviour, of contract, of persisted format, or of UI with a design choice; the tests suffice on a single, local effect, or a fix with a regression test — write `Barra: não aplicável (<por que os testes bastam>)` there (EN: `Bar: not applicable (<why the tests suffice>)`). `cerne feature approve F-NNNN --check` reads the spec's `Nível:` line and the stamped `## Custo` anchors and prints an `Advice` section — it shows the Gauntlet cost measured in your own project: `gauntlet-cost` (what a round cost in this project, overall and per level, or that there are not enough measured features yet), `light-with-bar` (a `leve` spec naming a bar: the tests may suffice) and `standard-without-bar` (a `padrão`/`avançado` spec with `não aplicável`: the justification the human accepts). Advice only — it never refuses the approve; the bar stays the human's call. For example, in cerne's own batch F-0368..F-0386, critic and judge took ~8% of a feature's weighted cost, up to ~22% on the small ones — a figure of that project, not the rule: read your own in the check.

### Implementation — builders, then a critic, then a judge

Three roles, three separate agents. Keeping them separate *is* the protocol — one agent playing two collapses it back into self-scoring, and "I will reread my own diff with fresh eyes" is that collapse:

- **builders** implement the plan TDD (red test → minimal green → commit), one concern per commit.
- **A fresh-context critic** attacks the finished diff. It is never the builder and never inherits the build conversation: whoever wrote the thing rationalizes it, and whoever watched it being written adopts its framing. Spawn it as a separate agent, hand it one file path (the diff or artifact written to disk) under the rule "read exactly this file, do not run git, do not read the repository", and delimit the artifact explicitly in the prompt (`=== DIFF (início) === … === DIFF (fim) ===`) — a fresh prompt inside your own session is not fresh context, and without the fence your own instructions are read as part of what is being judged. Demand the exact excerpt behind each finding; one without an excerpt is unverifiable. Capture the artifact the way its consumer receives it — the rendered runtime value, the served page, the real command output — never as a cut from the source when an assembly layer (concatenation, template, escape) stands between the two: that layer resolves away in the product but survives in the excerpt, handing the critic defects the consumer never sees.
- **A blind judge** compares your artifact against the bar. Write the two to neutrally named files, vary which position yours takes, and strip what gives it away (feature ids, paths, headings naming the origin). The bar comes out by the same consumer path, never from the source. When a finding from judge or critic is about form — rendering, escape, truncation, assembly residue — verify it against the runtime before it becomes a correction, a debt or a feature: an extraction artifact yields exactly this kind of plausible, specific finding. Ask one question — the job, named ("which text instructs an implementing agent better", "which rule is more robust") — and require the verdict as a fixed last line: `VEREDITO: A`, `VEREDITO: B` or `VEREDITO: EMPATE`. A verdict you have to interpret is one you will interpret in your own favour; any answer without that line counts as a defeat. A judge briefed in English may end in `VERDICT: A`, `VERDICT: B` or `VERDICT: TIE`; both count.

Every critic finding gets an explicit disposition, on the record: **corrected**, **refuted with evidence** (the existing code already handles it — name the `file:line`), or **accepted as a documented limit** (a declared debt or a follow-up feature). "Considered" is not a disposition; a finding that quietly disappears is a defect you chose to ship.

The judge decides the exit — **win or tie** — and you use a new judge every round: one that already ruled on your artifact defends its verdict instead of rereading it. A defeat produces corrections and another round; never a fixed number of rounds, and never a quiet swap for an easier bar (changing the bar is a spec change, not a round). The only way to stop while losing is an explicit human decision, recorded. Expect the judge to find real holes in the bar itself — route those as a separate improvement (a new feature, or a note), never fix the bar inside the delivery it is judging.

### Closing — the result carries the proof

`result.md` maps each numbered spec criterion to its evidence and must cite the number in words — `critério N` — because that literal citation is what `cerne lint` looks for: the `result-missing-evidence` rule flags an implemented feature whose result never mentions a criterion the spec numbered. Evidence is a test name, a `file:line`, a number; "atendido" on its own is an assertion. In an English project the citation is `criterion N` (`criteria 1-3` for a range).

Then record the loop under its own heading, one line per round:

```
## Gauntlet
Barra: <referência + acesso>
Rodada <n> — <vitória|derrota|empate>: "<citação curta do veredito do juiz>"
Achados do crítico: <n> — corrigidos <…>; refutados <… com file:line>; aceitos como limite <…>

Bar: <reference + access>
Round <n> — <win|loss|tie>: "<short quote of the judge's verdict>"
Critic findings: <n> — fixed <…>; refuted <… with file:line>; accepted as a limit <…>
```

The quoted verdict is what makes the record checkable at the human `accept` gate: a Gauntlet section with no quoted verdict per round and no disposition per finding cannot be told apart from a loop that never ran.

The critic's bundle: `cerne gauntlet artifact F-NNNN --out <file>` writes one file with the spec criteria, the plan contracts and the branch diff without noise (`ui/dist` and `docs.lock` are left out; `--base`, `--exclude` and `--notes` adjust it). For a feature already merged (several MRs, proof from runtime steps) pass `--commits` (the diff of each non-merge commit on the base that cites the id, listed on stderr) and `--evidence <file>` (repeatable, each whole in its own fence before the diff), so the critic does not flag as missing the proof that exists.

Recording the loop: `cerne gauntlet record F-NNNN --verdict <judge-reply-file> --ours A|B` writes the next `Rodada N` line into the result's `## Gauntlet` in `.docs/` (win, loss or tie for your side, from the reply's last `VEREDITO: A|B|EMPATE` line; the quote is the last quoted line before it, or `--quote`), and `--critic "<line>"` appends the `Achados do crítico` line; then `cerne push`. Do not hand-write those lines. In an English project it writes `Round N — win|loss|tie` and `Critic findings:`, and it reads `VERDICT: A|B|TIE` as well.

Cost per role (F-0384, F-0396): `cerne cost F-NNNN` and its `--stamp` recognise the critic and the judge from their transcripts — a judge ends in the verdict line or was asked for it, a critic is a `code-reviewer` or read the package's criteria and diff fences, inline or from the artifact file — so they land in the `## Custo` breakdown without a manual step. `cerne cost attribute <agent-id> F-NNNN --role critic|judge` stays for the agent the recognition misses, and a bound role wins. For Gauntlets from before this, `cerne cost backfill-roles` reports what the transcripts can recover (no write), and lists the agent ids per feature to review (ids only, never prompt text); `--apply` records the roles and completes each anchor (an implemented feature's result, or an erratum for a done one) and, after a failure, a re-run finishes what is missing. A wrongly classified agent is undone by `cerne cost attribute <agent-id> F-NNNN --role other` (the later bind wins). The `code-reviewer` rule also counts a non-Gauntlet review, such as a spec critic, as a critic.

`cerne feature complete` itself refuses a result whose record the lint would flag (a numbered criterion never cited, or no valid `## Gauntlet`), and `--force` does not cross it. Fix the result while the doc is still editable: once the feature is `implemented` the result is frozen out of `.docs/` — until the `accept` it changes only through `cerne feature amend` (see **Errata** below).

A critic-only pass (no judge) goes on the `Achados do crítico` line, never on a `Rodada N` line — a `Rodada N` line must carry the judge's quoted verdict. In English: the `Critic findings` line, never a `Round N` line.
