## Q: What is cerne? What does cerne do? How do I start using cerne?
cerne is an engineering workflow for software built with AI agents, in one local binary: a CLI and a web UI (`cerne ui`). What it does: keep the living documentation, separating the current state from history. The lifecycle of features, decisions and references is structured data in a git backend; `cerne pull` writes only the current state to a gitignored `.docs/` folder that agents read. It does not run in the cloud. Start with `cerne init` at the project root, or try a sample with `cerne demo`; `cerne guide` lists every command.

## Q: A command fails with "cache clone belongs to another backend". What now?
Two projects on this machine share one `project_id`, and the local cache is keyed by that id alone, so the clone in the cache is the other project's. cerne refuses to read or write through it, and never deletes it (the cache also holds rooms and messages). Give this project its own cache with `CERNE_CACHE_DIR=<dir>`, or a distinct `project_id` in its `.cernerc`. `cerne demo` already picks `taskflow-2`, `taskflow-3`… when `taskflow` is taken.

## Q: A command fails with "the folder does not accept writes" (permission denied on the cache, or search fails). What now?
The cache folder, or the local backend folder, is read-only for this process, typically an agent sandbox (Codex, for one) that only lets the project folder and /tmp be written. Nothing is corrupt and nothing needs deleting. Make the folders named in the message writable (the cache, `CERNE_CACHE_DIR` when set; for a local backend, its data folder, `CERNE_DATA_DIR` when set), or point `CERNE_CACHE_DIR` at a writable path, then re-run.

## Q: Which command do I run first? I just installed cerne.
Read the top-level help (run cerne with no arguments): the first section, "Start here", holds the on-ramp. `cerne init` sets up a project (or `cerne demo` creates a sample one to explore), `cerne ui` opens the dashboard, `cerne import` brings in an existing documentation tree, and `cerne guide "<what you want to do>"` answers any later question. The other sections group the rest by journey: read the state, author and move the work, sync with the backend, agents and coordination, administration.

## Q: How do I close a feature? One command or two?
Fill the result, `cerne push`, then `cerne feature complete <F-id>`: it moves the feature to implemented and stamps its token cost (`## Custo`) in the same command, the same stamp as `cerne cost <F-id> --stamp`. If the transition refuses, nothing is stamped. If the stamp cannot be made it prints `warning: cost not stamped: …` and still exits 0, because the feature is already implemented: when no session on this machine is bound to it, run `cerne cost <F-id> --stamp` from the machine that ran the work. `--no-stamp` skips the stamp. The output ends with one Next step block: the human `cerne feature accept <F-id>` and, when the feature has a PR link, the delivery line. Marking the PR ready for review is not done by cerne. Run the complete as soon as the PR is open: human review starts when the card is in Ready, so do not wait for CI or the merge.

## Q: Can merging the PR accept the feature? How does accept on merge work?
Yes, when the project opts in with `[gates] accept = "merge"` in `.cernerc` and has a `[delivery] forge` (`github`, `gitlab` or `gitea`). The human's merge of the card's delivery PR into the default branch is then the acceptance, for features, tasks and bugs alike. cerne only records it: `cerne feature accept --merged` asks the forge about every implemented card with a delivery PR (`cerne feature accept <id> --merged` about one) and moves each merged one to done. The event carries `via: merge`, the PR and the merge time, with the human as the actor; `cerne show <id>` prints `accepted: on merge of <PR>`. An agent may run `--merged`, and `cerne feature wait <id> --for done` runs it each round, so the session that delivered wakes up once the human merges. A PR still open, closed without merge, merged into another branch (a stacked PR), or on another repository or host stays implemented, with one line saying why. The accept typed without `--merged` stays a human act, the way out for a delivery with no PR. An agent never merges the PR itself: under this gate the pre-tool shell hook refuses `gh pr merge`, `glab mr merge`, `tea pulls merge` and an API call to a merge endpoint in an agent's shell. The hook does not see a merge done another way: a tool a harness exposes outside the shell (an auto-merge behind an MCP tool, say), a `git push` of the PR's commits to the default branch, or a raw HTTP call. Like `CERNE_ACTOR`, the guard stops the configured agent; it does not prove who merged, since the agent and the human usually share one forge login.

## Q: The human rejected a Ready card, found a bug, or accepted by mistake. How does a card go back from Done to Ready, or from Ready to In development?
`cerne feature revert <id> --reason "<why>"` walks the card one step back: `done` → `implemented` undoes an acceptance, `implemented` → `in_development` sends the delivery back to development, and `approved` → `candidate` undoes an approval. Each step is a human act (refused in an agent's shell by default, `[gates] revert`), the reason goes on the `feature.reverted` event, and the spec, plan, result and delivery links stay as they were: the fix usually goes in the same PR, and the next `cerne feature complete` runs every gate again. In `cerne ui` the human drags the card from Done to Ready, or from Ready to In development, and types the reason in the dialog the drop opens (cancel or a blank reason changes nothing); the feature page offers Revert on Ready and Done too. Under `[gates] accept = "merge"`, a card whose acceptance on merge was reverted is not accepted again from the same PR: link a new delivery with `cerne feature deliver <id> --mr <url>`, or a human accepts by hand. The revert of Done does not reopen the pendings, ideas or tasks the acceptance closed.

## Q: I asked a human to approve or accept. How does the agent know when they did?
Leave `cerne feature wait <F-id> --for approved` (after the complete, `--for done`) running in the background, then stop. When the human acts, it exits with one line — the transition, who made it and when, and the next step — and a harness that wakes the session when a background command ends (interactive Claude Code does) brings the agent back without anyone typing. Exit 2 means the state can no longer be reached (rejected, superseded), exit 3 the `--timeout` (24h by default; `0` checks once), exit 4 a channel message addressed to the session and not yet shown to it (the human's from the card's page, say): it prints the message, how to answer and the wait to run again. It only fetches the backend clone, never pulls, so `.docs/` is untouched. Without the wait the move still reaches the session: a human's approve, accept, reject, revert or supersede leaves a card notice for every session of this machine that worked on the card (the ones the card page's Agents panel lists), and the session sees that same line once, ahead of the channel, at its next turn or tool call (F-0504). So an agent that comes back to "go on" already knows the new state; the wait is what wakes a stopped session. In a harness without background commands, just stop: the human tells the agent, and the card notice comes with the next turn. The gate stays human: the agent never runs the approve or the accept itself. Under `[gates] accept = "merge"`, `--for done` also asks the forge each round and records the human's merge of the card's PR, the one write it makes.

## Q: Can I amend a spec in development? Does the amend need re-approval? Why was the amend refused because another session is working on the card?
Yes: `cerne feature amend F-NNNN --doc spec --file spec.md --reason "<why>"`. In development the amend takes effect at once, with no re-approval: only an approved spec goes stale, and `cerne feature approve` refuses a feature already in development. The plan and the live children were written against the previous text, so re-read them. The amend is refused, and writes nothing, when another session or another actor has active work on the card or on a live child: it lists each work with its actor, session and last signal, what the amend causes in that state, and the plan and children written against the current text. Confirm with that session first; `--force` amends anyway and records `guard: forced` with the works' ids on the event. A work of your own actor with no session bound on this machine only warns.

## Q: How do I change a project setting from the CLI?
Use `cerne settings set <key> <value> --scope project`. `--scope` is required: `project` writes `.cernerc`, `host` writes the user's `settings.toml`. See every key, its value and where it comes from with `cerne settings list`, read one with `cerne settings get <key>`, remove an override with `cerne settings unset <key> --scope project`. Owner-only keys such as `gates.gauntlet` refuse an agent (`CERNE_ACTOR=agent`): ask the owner.

## Q: Where is the cerne UI API? Which URL does the dashboard call?
`cerne ui` serves every project from one process, so each route is under `/api/projects/<pid>/…`, where `<pid>` is the project id of `.cernerc`. `GET /api/projects` lists the registered ids. A bare `/api/<route>` is not the UI API. The default port is 7717 (`cerne ui --port`).

## Q: Why does a request to the cerne ui API answer 403?
`cerne ui` answers only on this machine. Every request, reads included, needs a loopback `Host` (`127.0.0.1`, `localhost` or `[::1]`, any port), and a write (any method but GET and HEAD) also needs an `Origin`, when the request sends one, that names that same host. A domain name rebound to 127.0.0.1 gets 403 and reads or writes nothing; so does a forwarded hostname (a Codespaces port, a reverse proxy): open the UI at the loopback address. A page on another site gets 403 on a write. Call `http://127.0.0.1:7717/api/projects/<pid>/…`: the CLI and curl send no `Origin` and pass. Some routes also check the body type (JSON, or markdown for the Vault's saves). The remote `cerne serve` does not apply this check.

## Q: Can the UI edit a note, decision or runbook? Why did a save answer 409, 422, 400, 403 or 413?
Yes: the Vault (`#/vault` in `cerne ui`) edits the open document in place — a live feature's spec, plan or result, and an active decision, note or runbook. The save goes through the same core as the CLI, as a human, with a commit and a push. Each read carries the sha256 of the document (`content_hash`, or `docs_hash` per feature document) and the editor sends it back as `If-Match` on `PUT /api/projects/<pid>/notes/<id>/content` (also `decisions/`, `runbooks/` and `features/<id>/docs/<doc>`). A 409 means the backend document changed since it was loaded: nothing was written, and the body carries the current `content` and its `content_hash`. A superseded or retired entity answers 422 `entity is not live — append an errata instead`: history takes `cerne note errata` (or `cerne decision errata`, `cerne runbook errata`). A 400 names a `cerne_id` in the frontmatter that is not the entity's own: `cerne push` routes a document by it, so the save refuses it. A 403 means the write did not come from `cerne ui` on this machine (it needs a loopback host and a same-origin markdown request). A 413 means the body is over 4 MiB.

## Q: How is the before and after of a process marker dated?
A process marker is a decision with facet `process` and component `metric`. `cerne stats --process` judges the 28 days before and after it, and the date it uses is when the decision was created (`cerne decision new`), not when the change shipped. Create the marker decision the day the change goes live, or the window is wrong.

## Q: How does the judge's cost reach the feature? Why is the judge missing from by_role?
The Gauntlet's critic and judge run no cerne command, but `cerne cost <feature-id>` and `cerne cost --stamp` recognise them from their transcripts: a judge ends its last reply in the verdict line (`VEREDITO: A|B|EMPATE`) or was asked for it, and a critic is a `code-reviewer` or read the criteria and diff fences of the Gauntlet package, in its first message or in a file it read. Nothing to run by hand. A role bound with `cerne cost attribute <agent-id> <feature-id> --role judge` still wins over that recognition. For Gauntlets already done, `cerne cost backfill-roles` reports the roles it can recover (add `--apply` to record them and complete each anchor; a done feature gets an erratum with the `## Custo` block). The By role block of `cerne cost <feature-id>` lists builder, critic, judge, other and main.

## Q: A subagent ran feature start. Why does the cost stamp say nothing to stamp?
The bind hook binds the subagent that runs `cerne feature start <F-id>` under its own key, so `cerne feature complete <F-id>` and `cerne cost <F-id> --stamp` count its tokens with no extra step, even when the output was piped or redirected (`cerne feature start T-0005 2>&1 | tail -5`): without the transition line in the output, the hook checks that the feature is now in_development. A start the hook never saw (an older cerne, hooks not installed, another machine) leaves the subagent unbound: run `cerne cost attribute <agent-id> <F-id> --session <session-id>`, then `cerne cost <F-id> --stamp`. The agent id is the `agent-<agent-id>.jsonl` file under the session's `subagents/` folder.

## Q: How do I get the id of an idea I just created?
`cerne idea new <title>` prints the id on its first line (`I-0007 created (active) — …`); the optional body comes from `--file` or stdin. Lost it? `cerne idea list` shows ids, newest first (`--state resolved|dropped|promoted|all`, `--component <c>`). Turn it into a candidate, classified in the same command, with `cerne idea promote <id> --facet <f> --component <c> [--capability <C-id>]` (a card it would leave with no tag, or with no capability once the project has a taxonomy, is refused unless `--allow-incomplete`), point it at a feature that is already live with `cerne idea link <id> <F-id>` (`cerne idea unlink <id>` undoes it); promoted by mistake, `cerne idea unpromote <id>` rejects the candidate it created and returns the idea to active, close one something else already delivered with `cerne idea resolve <id>`, or drop it with `cerne idea drop <id> --reason "<why>"`. A promoted or linked idea follows its feature: the accept resolves it, a reject reopens it. Ideas stored before title and body: `cerne idea migrate --dry-run`, then `cerne idea migrate`.

## Q: cerne next shows no cost stamp line for a feature I worked on in Codex or another harness. Is it stuck?
No. `cerne cost` reads Claude Code transcripts only, so a session bound under another harness cannot be stamped, and `cerne next` does not list it under FINISH DELIVERY (that section holds only runnable commands: `cerne cost <F-id> --stamp` when the stamp would run, `cerne feature deliver <F-id> --mr <url>` when no PR link is recorded). With the delivery link in, the feature moves to WAITING FOR HUMAN ACCEPT (WAITING FOR THE MERGE under `[gates] accept = "merge"`). An unreadable cost ledger still shows as `cost check failed: …`. `cerne feature complete` says the same in its `cost not stamped: … nothing to run` line: there is no command to run.

## Q: How do I turn the Gauntlet off? Light mode without the bar and the judge.
The Gauntlet is the setting `gates.gauntlet` (`on` or `off`). The owner flips it in the Settings screen of `cerne ui` or with `cerne settings set gates.gauntlet off --scope project`; the command refuses an agent. With it off, `cerne feature approve` takes a spec with no `Barra:` line and `cerne feature complete` takes a result with no `## Gauntlet` section, but each criterion still needs its evidence. `cerne status` prints `Gauntlet: off (light mode)`. An agent never switches it to get past a gate.

## Q: How do I hand my work to another agent? Pass the baton.
Record the handoff with `cerne work handoff <W-id> --next "<next step>" --file brief.md --evidence <ref>,<ref>`; it prints an `HO-` code. Pass only that code. The receiver runs `cerne handoff take <HO-id>`, which opens its own work, closes yours and prints the brief. Review pending ones with `cerne handoff list`, withdraw with `cerne handoff cancel <HO-id>`. Add `--if "<condition> → <action>"` once per contingency.

## Q: How do I register an external source, an article, a link or a spec?
`cerne reference new "<title>" --url <url> --informs F-0001,D-0002 --file summary.md` (or pipe the summary on stdin). The reference is marked external, its text is indexed so `cerne ask` cites it, and `--informs` links it to the entities it motivated. A bare URL in a decision or feature makes `cerne lint` report `unregistered-source`. A live reference with the same URL is refused unless `--force`.

## Q: How do I know a registered source went down or changed? Reference check.
`cerne reference check` requests the URL of every current external reference (or only `cerne reference check R-0001`) and prints one line each: `ok`, `changed`, `gone` or `transient`, with the entities a changed or gone source informs. The first check only records the baseline. Confirm a changed page with `cerne reference keep R-0001`. A gone source (404, 410, domain missing) makes `cerne lint` report the blocking `reference-gone`; retire it with `cerne reference retire R-0001 --reason "source gone"`. Only `reference check`, `cerne reference archive` and, with `references.archive` on, `cerne reference new` use the network; lint, pull and push read what they recorded (a gone or changed line and the `reference-gone` finding also show the archived copy, when there is one).

## Q: How do I keep an archived copy of a source? Reference archive, the Wayback Machine.
`cerne reference archive` sends the URL of each current external reference with no copy yet or a pending one (or only `cerne reference archive R-0001`) to the Wayback Machine and records the link and date of the copy: the capture nearest the day the source was registered when the archive has one, else a new copy. With the setting on, `cerne reference new` also uses the network: it does the same when it registers a source. Both need `references.archive`, a human-only setting that is off by default: the owner turns it on in the Settings screen of `cerne ui`, and an agent never does. `cerne reference new "<title>" --url <url> --no-archive` keeps a source from ever being sent, and so does every other reference with the same URL; `cerne reference archive --opt-out R-0001` does the same for an existing one (it needs ids, reaches no network and works with the setting off). `cerne reference archive --dry-run` lists what would be sent and sends nothing. Only the URL leaves the machine, and only for a page that answers 200 to an anonymous request: internal hosts, `unregistered_source_ignore` items, share-link hosts (Google Docs, Drive, SharePoint, Dropbox, Notion and the like), URLs with credentials or a secret parameter, names that resolve to a private address and pages an anonymous request cannot read (401, 403, 404, a login page) are skipped. Public here means only that: a private page that answers 200 to anyone holding its link on another host still passes, so review `cerne reference archive --dry-run` before the first real run. `cerne show R-0001` and `cerne reference list` show the copy.

## Q: Note or reference? Where does guidance go and where does the source go?
Each type keeps one thing. A note (`N-`) keeps the guidance: what to do or avoid in this project. A reference (`R-`) keeps the source: the article, RFC, vendor doc or spec someone else wrote that backs it. When guidance rests on a source, the note points to the reference: `cerne reference new "<title>" --url <url> --informs N-NNNN` registers a new source for the note, and `cerne reference link R-NNNN --informs N-NNNN` links one already registered. Do not paste the source into the note, and do not write guidance in the reference summary: the agent receives the short guidance and opens the source only when it needs the grounds.

## Q: Why does cerne ui serve an old screen or a 404 after I reinstalled cerne?
A `cerne ui` process keeps serving the embedded UI and API of the binary it started with. The panel notices when its command resolves to another binary on disk (an upgrade through Homebrew or the install script, or a new local build) and shows a notice with a Restart the panel button: it restarts into the new binary on the same port, keeps the other registered projects and reloads the open tabs. A `cerne ui` of the installed binary run in another project restarts the panel by itself. A panel started by a release from before this notice has neither: stop that process (it listens on port 7717) and start `cerne ui` again.

## Q: How do I start working on a feature and finish it?
`cerne feature new "<title>"` registers the candidate, `cerne pull` materializes `.docs/`, fill the spec and plan, `cerne push`, then the human runs `cerne feature approve <F-id>`. The builder runs `cerne feature start <F-id>`, writes the result, `cerne push`, then `cerne feature complete <F-id>`. `cerne feature accept <F-id>` is the human validation step that makes it done.

## Q: Do cerne's hooks work in Cursor? What does the third-party setting give me?
Yes, through Cursor's import of the project's `.claude` hooks, the setting "Include Third-Party Plugins, Skills, and Other Configs" (Cursor Settings, Agents, Third-Party Imports; on by default). With it on, the same hooks run in Cursor: the registration rules and live board at session start, the work gate, the session binding after `cerne work start` or `cerne feature start`, the provenance reminder, and the end-of-turn closeout, which Cursor submits as a follow-up message. Cursor's agent shells carry `CURSOR_AGENT=1`, so `cerne feature approve` and `cerne feature accept` refuse a Cursor agent as they refuse a Claude Code one. With the setting off, only what `cerne hook install --provider cursor` writes under `.cursor/` reaches Cursor: `.cursor/rules/cerne.mdc`, the session-start board from `.cursor/hooks.json`, the sandbox folders in `.cursor/sandbox.json` and the `cerne mcp` server in `.cursor/mcp.json`.

## Q: How do I connect codex, cursor or gemini to my project? Which agents did cerne init connect?
`cerne init` connects Claude Code (guide and hooks) and delivers the authoring guide to every other agent whose folder (`.cursor/`, `.codex/`, `.gemini/`) already exists in the project; it ends with `Agents connected: claude.` and `To connect ...` naming the others. To connect them, run `cerne hook install --provider <name>` (creates the agent's folder and hooks), then `cerne skill install` (the authoring guide). `cerne init --verbose` lists every installed file.

## Q: How do I make GitHub Copilot work with cerne? Which of cerne's hooks does it get?
Run `cerne hook install --provider copilot` and `cerne skill install` (Copilot is also picked up automatically when the project has `.github/copilot-instructions.md`, `.github/hooks/`, `.github/skills/` or `.github/agents/`). They write `.github/hooks/cerne.json` (session-start board, work gate, session binding, provenance reminder, stop closeout), the authoring skill under `.github/skills/cerne-authoring/`, the rules in `.github/instructions/cerne.instructions.md` (the project's own `copilot-instructions.md` is not touched) and the read-only `cerne` server in the root `.mcp.json`. In `copilot -p` the repository hooks only load in a trusted folder (`--trust-folder`). The Copilot cloud agent does not read `.mcp.json`: paste the block the install prints into the repository settings and install the cerne binary in its environment. Degraded rows and what is verified: see the next question.

## Q: What is degraded or unverified when cerne runs on GitHub Copilot?
Copilot degradations (docs/provider-parity.md): Handoff code through compaction (preCompact is notification-only); Document author (CERNE_PROVIDER, F-0375) (reaches the hooks, not the bash shell); Subagents with live board (no subagent hook); Notes matching the prompt (B-0020) (no verified prompt-submit event wired); Stop closeout (the block decision was never exercised live, treat it as unverified); Wake an idle session (F-0491) (no documented way to open a turn in an idle session: a channel message waits for the next contact point); Double execution with the .claude hooks (Copilot CLI runs both sets and ignores the Claude-format output, so only side effects repeat). Copilot's bash shell is marked `COPILOT_CLI=1`, so `cerne feature approve` and `cerne feature accept` refuse it as they refuse Claude Code, verified on Copilot CLI 1.0.112 only; VS Code agent mode and the cloud agent are unverified. `.github/hooks/cerne.json` belongs to cerne and is rewritten whole when it differs (keep team hooks in their own file there); a corrupt `cerne.json` or `.mcp.json` is left untouched and reported as skipped.

## Q: Does each task of an epic need its own approve and accept? Which bar does a task declare?
No. Decompose an approved epic with `cerne task new "<step>" --parent E-NNNN --file spec.md`: the task is born approved. The human's `cerne feature approve E-NNNN` also approves every candidate child that passes `cerne feature approve <id> --check`, and `cerne feature accept E-NNNN` also accepts every implemented task, so an epic costs two human acts whatever the number of tasks; an F- child keeps its own accept. Each task declares its own bar in its spec: a named bar (its result records the round), `Barra: não aplicável (…)`, `Barra: dispensada por decisão humana (…)`, or `Barra: herdada de E-NNNN` (EN: `Bar: inherited from E-NNNN`), which needs a named bar on the parent and puts the round in the parent's result. `cerne feature start T-NNNN` refuses a spec with no valid bar.

## Q: What do I do right after feature new? What is the Next step block?
`cerne feature new`, `cerne epic new` and `cerne idea promote` end with a Next step block that lists what the candidate still lacks, in order: the real spec (when it was seeded from `--context`), the tags, the capability (when the project curates a taxonomy), then `cerne feature approve <F-id> --check`, and last the human approve, where an agent stops without implementing. `cerne feature start` ends with its own block: consult the active notes with `cerne note list` before the code, keep `plan.md` and `result.md` current, `cerne sync` at each milestone. The blocks are the command's own output, so every harness (Claude Code, Cursor, Codex, Gemini) gets the same text, with or without hooks.

## Q: How do I read the project state without loading everything?
`cerne brief` is the cheapest map (id, state, title). `cerne status --active` shows only active work, `cerne next` the next action per feature plus documentation debts. Read one entity with `cerne show <id>`, search by subject with `cerne search "<query>"`.

## Q: Where do the learnings from a result go? How do I reuse what a past agent learned?
A result's learnings are history and do not reach the next agent by themselves. `cerne feature complete` lists them. A durable one becomes a note with `cerne note new "<title>" --informs <F-id> --component <topic>`; first find a note that already covers it (`cerne note list --path <file>` or `cerne search "<terms>"`): complement it with `cerne note errata <N-old> ...`, or if it contradicts, replace it with `cerne note supersede <N-old> --by <N-new> --reason "..."`; none durable: `cerne feature learnings --skip <F-id>`. `cerne feature learnings` lists, read-only, the past features nobody triaged yet concluded since 2026-11-13 and counts the older ones apart; `--since 2026-01-01` lists them, `--feature F-NNNN` shows one.

## Q: What can cerne do? Which features exist?
Run `cerne guide` with no question: it prints the catalog of every command, grouped by area, straight from the command tree, so it is never stale. Then `cerne guide "<feature>"` (for example `cerne guide "gauntlet"` or `cerne guide "room"`) returns how to use it: the reference file of that area and the command help. `cerne guide --topics` lists the topics; a command name alone (`cerne guide "room"`) brings its help. The skill's `reference/` folder holds the same detail for agents that read files.

## Q: A human asked me to register this demand. How do I record who asked? What is the origin of a card?
Every new feature, epic or task stores `origin`: `agent` when your session runs with `CERNE_ACTOR=agent`, `human` otherwise. When the human asked and you only ran the command, pass their words: `cerne feature new "<title>" --context "..." --on-behalf "<quote of the human's request>"` (also on `cerne epic new` and `cerne task new`). That records origin `human` and the quote on the creation event; a blank quote is refused. Read it with `cerne show <id>` and filter with `cerne feature list --origin human|agent`. Cards created before the field have no origin.

## Q: A human reported a bug or a fix. Do I open a feature? How do I report a bug with cerne?
No feature: use a bug report. `cerne bug new "<what breaks>" --context "<what happens, where>" --steps "<numbered steps>" --expected "<should happen × what happened>" --on-behalf "<the human's words>"` mints a `B-` card with a three-section spec (Context, Steps to reproduce, Expected × actual; each filled by its flag) and the regression-test bar already filled. A human origin means the report is the approval: the card is born `approved`, so run `cerne feature start B-NNNN` right away, no plan and no approve. Add `--fixes F-NNNN` to link the delivered feature and inherit its tags. A bug you found yourself (no `--on-behalf`) is born `candidate`: ask a human to run `cerne feature approve B-NNNN`. Completing needs a real `result.md` and accept stays human. A person using the UI opens "Reportar correção" (`#/bug`, linked on the Manage page).

## Q: How do I update cerne? I updated the cerne binary but the project still has the old skill or hooks. How do they catch up?
Run `cerne update` inside the project. It updates the binary the way it was installed: Homebrew upgrades it; a script or hand install downloads the latest release, checks it against `SHA256SUMS` and swaps it in place. Then the new binary renews the hooks and the guide of the agents already connected, the same as `cerne hook install` plus `cerne skill install`, and connects no new agent. It closes with one line per part (binary, hooks, guide): updated, up to date, or not done with the reason and the command; the exit code is 0 only when nothing was left not done. The AUR package `cerne-bin` (`/usr/bin/cerne`) is pacman's: `cerne update` leaves it and prints `yay -Syu cerne-bin`. A Scoop install is Scoop's: `cerne update` leaves it and prints `scoop update cerne`. A local build, a `go install` or a folder you cannot write keeps its binary and names the command. An agent can run it too, but never replaces the binary: that part is the human's, in their own terminal. `cerne update --check` lists what is out of date, writing nothing and using no network. On a version without the command, update the binary first with `brew upgrade henriquesakata/tap/cerne` or the install script.

The canonical skills (`cerne-authoring`, `cerne-self-learning`) and the managed hook scripts are embedded in the binary, so a new binary alone changes nothing on disk. While the project's files are older than the binary, `cerne next` opens with a line asking for `cerne update`, and so does the session-start hook. With `sync_skills = true` in `.cernerc`, `cerne pull` and the session-start hook rewrite the stale canonical skills by themselves. The hooks and the guide of a connected agent also renew by themselves, at the session start and in `cerne next`, when every managed file of that agent is one a past release wrote (no network, no new agent connected, a line says what was renewed); when any file was edited or written by a newer cerne, cerne touches nothing of that agent and only warns, naming the file, until you run `cerne update`, which does not keep local edits to managed hooks (review the diff). To turn the automatic renewal off: `cerne settings set hooks.auto_refresh false` (`--scope host` for every project on the machine). `cerne harness` shows the divergence per item.

## Q: Is someone already on this? Has a work already covered it?
Run `cerne search --works "<subject>"`: it lists only the matching works (id, state, actor, title; active first, up to 50), found by title, closing note, handoff and decision log. Words match as prefixes ("rota" finds "rotação"), all words first and any word when none has them all. The plain `cerne search "<subject>"` shows the same as a `Works:` group after its usual results, capped at 5 with a line saying how many more match. `--json` carries `works` and `works_total`. Active works are in progress now; done ones tell you who already covered it (`cerne show <W-id>` for the detail). If the first line says the search index was last synced long ago, `cerne pull` first: works written on other machines may be missing.

## Q: Who is working on what at the start of a session? Is the in-progress board stale?
The session-start hook (`cerne hook channel --point session-start`) prints the in-progress board read from the shared clone, not from the checkout's `.docs/CONTEXT.md`: the same active work, idle-work line and pending handoffs as the "In progress" section of `CONTEXT.md`, or one `- no active work` line. If the clone was last fetched more than 24 h ago it adds one line saying so; run `cerne pull` to refresh. `cerne work list` shows the same state on demand. The subagent point prints no board (it inherits the parent's context).

## Q: How do I check a draft spec before registering it? What does the chat's "Pedir correção" button do?
`cerne spec check --file <draft.md>` (or the body on stdin) lints a spec body without writing anything: the template sections that are missing, the Gauntlet bar line when absent or malformed (skipped in light mode) and open clarifications, which are warnings only. It exits 1 on an error and 0 otherwise; `--json` prints the same list. It is the check `cerne feature approve --check` and the `incomplete-doc` lint run. The Backlog chat runs it on every proposal block at the end of a turn and lists the issues on the proposal card; "Pedir correção" sends them back to the agent as your next message, and nothing is corrected behind your back.

## Q: cerne feature approve says "human gate", but I am the human. What now?
The command ran in a shell cerne reads as an agent's: `CERNE_ACTOR=agent` (stamped by `cerne hook install`), or, with no `CERNE_ACTOR`, the shell marker of Claude Code (`CLAUDECODE=1`), Cursor (`CURSOR_AGENT=1`), Copilot CLI (`COPILOT_CLI=1`) or Codex (`CODEX_THREAD_ID`, any non-empty value). The same refusal stops `cerne feature accept`, a revert and the human-only settings such as `gates.gauntlet`. Run the command in your own terminal, or declare yourself with the prefix: `CERNE_ACTOR=human cerne feature approve <id>`. A non-empty `CERNE_ACTOR` always wins over the markers. An agent never sets it: the gate exists so that an agent does not approve its own spec.

## Q: Why does a work, event or handoff author look like m-1a2b3c4d instead of my login?
cerne never records or shows a login or machine name as an author. `cerne work start` records `m-<8hex>` (the machine pseudonym: the first 8 hex of the SHA-256 of the lowercased `<user>@<host>`), or `agent:m-<8hex>` when `CERNE_ACTOR=agent`, or with no `CERNE_ACTOR` in a Claude Code, Cursor, Copilot CLI or Codex shell (`CLAUDECODE=1`, `CURSOR_AGENT=1`, `COPILOT_CLI=1`, `CODEX_THREAD_ID`, any non-empty value). A value with `@` given to `--agent` or `CERNE_ACTOR` is recorded as its pseudonym, and a value without `@` stays as it is. Records written before this rule keep their old text in the backend but are read as the pseudonym, so they still count as this machine's. `cerne work list` writes `session: on another machine or user (m-<8hex>)` for an active work of another pseudonym.

## Q: A new git worktree has no .docs/. How does an agent get the projection?
`.docs/` is gitignored, so a fresh worktree of a project that has its own `.cernerc` starts without it. The SessionStart hook (`cerne hook session-context`, every provider) builds `.docs/` itself from the local backend clone when `.docs/CONTEXT.md` is missing. It never contacts the backend and never resets the clone, so unpushed local state is safe; the context then carries one line saying the projection may be stale and that `cerne pull` refreshes it. If there is no clone yet, or the backend lock stays busy for a few seconds, the session still starts and the line says to run `cerne pull`. A worktree without its own `.cernerc` resolves to the main checkout (B-0016) and reads that checkout's `.docs/`, so nothing is built there.

## Q: I sent a message on the project channel and the UI says not delivered. When does an agent get it? Why does nobody answer?
A channel message reaches a session only at a contact point: session start, a subagent's start, the user's next prompt to that session, before each shell command and each Edit/Write (after the tool on Cursor, Gemini and Copilot), and the session's own `cerne next`, `cerne status --active` or `cerne msg read`. "Not delivered" means no live session of that work has passed one since the message was posted: an idle session gets it at its next prompt or tool call, and a work with no session on this machine is not waited for. A message the human sends is addressed to every session with live work: it comes back at each contact point, with the line telling the agent to answer with `cerne msg send "<text>"` or `cerne msg ack <seq>`, until it does. `cerne msg read` shows each message's state per work (not_delivered, delivered, answered). `hooks.prompt_notes` and `hooks.notes_on_bash` turn off only the notes, never the channel.

## Q: How do I turn off the note reminder the agent gets when I send a prompt?
Set `hooks.prompt_notes` to false: `cerne settings set hooks.prompt_notes false --scope project`. It is on by default. The UserPromptSubmit hook (cerne-prompt-notes.sh, installed by `cerne hook install`, Claude Code only) matches the prompt against the titles of active notes and runbooks in the local index and injects up to 3 `id — title` lines, once per session per id; read one with `cerne show <id>`. It never pulls or reindexes, so a stale index shows stale titles until the next `cerne pull`. The same hook also delivers the project channel's pending messages; turning the notes off leaves the channel on.

## Q: Do I have to repeat the title on the command line when the body already starts with a heading?
No. The `new` commands of notes, decisions, runbooks, references, features and bugs (`cerne note new` and its siblings) take the title from the body's first `# ` heading (after any frontmatter) when no title argument is given, from `--file` or piped stdin: `cerne note new --file nota.md`. A title argument, when given, still wins. The heading stays in the stored body, so the document shows it once. With no argument and no heading as the first line (a `# ` inside a code block or after other content does not count) the command refuses with "give a title or start the body with a `# ` heading"; a `--context`-only feature or bug still needs the title argument.

## Q: cerne runs gh or glab for another host and my GITLAB_TOKEN or GH_ENTERPRISE_TOKEN is not used. Why?
The committed `.cernerc` names the host (a `mirror.trackers` url, the `delivery.commit_url`), and gh and glab would send a token variable to whatever host they are pointed at, so cerne passes each one only to the host it belongs to. `GH_TOKEN` and `GITHUB_TOKEN` go only to github.com. `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` go only to the host in `GH_HOST`. `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN` and `OAUTH_TOKEN` go only to the host in `GITLAB_HOST`, else `GL_HOST`, else gitlab.com. Host names compare without case, scheme or port. Any other host gets the CLI's own login: run `gh auth login --hostname <host>` or `glab auth login --hostname <host>`, or set the host variable to that host, then run `cerne mirror sync` again.

## Q: How do I mirror cards to GitHub, GitLab, Gitea, Jira or Trello? Which credential does each tracker use?
A human adds the tracker to `mirror.trackers` (name, kind, url, label) and turns on `mirror.enabled` in the Settings screen of `cerne ui`; `cerne feature mirror <id> --title <title> --summary <summary>` then publishes a card, and `cerne mirror sync` keeps its issue in step. The url and the credential of each kind (no credential goes in `.cernerc`):
- `github`: `https://<host>/<owner>/<repo>`; the gh login, `gh auth login --hostname <host>`.
- `gitlab`: `https://<host>/<group>/<project>`; the glab login, `glab auth login --hostname <host>`.
- `gitea`: `https://<host>/<owner>/<repo>`; an access token in git credential for the host.
- `jira`: `https://<site>/browse/<PROJECT KEY>`; git credential for the site: the account e-mail and an API token on Cloud, a personal access token on Data Center.
- `trello`: `https://trello.com/b/<boardId>/<slug>`; git credential for `api.trello.com`: the API key as the username, the token as the password.
Store one with `printf 'protocol=https\nhost=<host>\nusername=<user>\npassword=<token>\n\n' | git credential approve`.

## Q: What does cerne next show on a new project? What are the first steps?
Until the first feature is accepted, `cerne next` opens with a FIRST STEPS block: ask your agent for a feature, approve its spec (`cerne ui` or `cerne feature approve <id>`), accept the delivery (`cerne feature accept <id>`). Each step is ticked from the project event log, nothing is stored, and the block links the first-week guide. The usual sections stay below it; after the first accept the block is gone.

## Q: What does cerne import tell me when it finishes, and can imported features start as done?
After `cerne import --yes` (and `cerne import --agent --ingest --yes`) the closing lists what came in by kind and by state, then two next steps: a `cerne search` over a word from the imported titles and the request to hand your agent for the first feature, plus the address of the first-week guide. A feature imported as delivered (a case with a result, or a status line saying it shipped) enters as `implemented`, waiting for your accept. Pass `--delivered-state done` to have it enter as `done` instead; `--delivered-state implemented` is the default. On a terminal, a dry-run import that finds delivered features and got no `--delivered-state` asks once which state to use and prints the flag to add when you apply; with `--yes` or with the flag given, it never asks. Without a terminal (an agent or a script) the dry-run does not ask: it prints `N delivered feature(s) will enter as implemented; add --delivered-state done to enter them as done.` The import writes only `<kind>.imported` events, never an approval or an accept, so the first steps in `cerne next` stay unchecked.

## Q: Does cerne import --agent map the skills and hooks that cerne installed?
No. The sources collected for the mapping prompt leave out what cerne writes into the project: the folders `cerne init` and `cerne skill install` fill whole (`.claude/hooks`, the `cerne-authoring` and `cerne-self-learning` skill copies for each agent, `.github/hooks`, `.github/instructions`), the `learned-*` skills under `.claude/skills/`, and the marked block in `AGENTS.md` and `GEMINI.md` (a file holding only that block is dropped). Your own skills, `CLAUDE.md` and the text you wrote around the block stay in.

## Q: cerne import --agent --ingest left items out as unanchored. Why, and how do I get them in?
Each item of the agent's plan carries `evidence`: one to three snippets copied literally from its `source` file, which prove the state it chose. The ingest checks every snippet against the file (whitespace and line breaks may differ) and only the items that pass are applied; the rest are listed under `Unanchored (left out)` with the reason: `no evidence`, `more than 3 evidence snippets`, `source not found: <file>` (the file is resolved against `--root`, default the project directory; a `#fragment` after the file name is ignored) or `evidence not found in <file>: "<snippet>"`. Nothing is applied for them even with `--yes`, and `.docs/import/.pending/plan.json` is kept: fix the `evidence` (or the wrong `source`) in that file and run `cerne import --agent --ingest` again. Items already imported (same source and title) are skipped, so only the corrected ones come in. An item with an invalid kind or state is a schema error and rejects the whole plan. For an applied entity, `cerne show <id>` prints `imported from:` and `anchor:` (`file:first-last` line ranges of each snippet). Each snippet is a short sentence of at least 12 characters (`evidence too short:` otherwise), and a source that is not a regular file inside the root, resolved through symlinks, is `source not found:` (`source too large:` over 10 MiB, `source unreadable:` when it cannot be read). Declared limits: the import key is source plus title, so a new mapping of the same file with rewritten titles imports notes, decisions, runbooks and references again (features keep the title guard), and the same happens when a folder-convention `cerne import` is followed by `cerne import --agent --ingest` over the same file with a different title; the dry-run, the default, shows the duplicate before `--yes`; a `#` in `source` always starts the fragment, so a file with `#` in its name is not found; an invalid UTF-8 byte in a snippet may fail to match (the lines are unaffected).

## Q: What do I do after installing cerne? What comes after init?
Run `cerne init` at the project root (or `cerne import --agent` when it already has docs), then follow the first steps it prints: open the dashboard (`cerne ui`), ask your agent for a small feature ("Use cerne to plan <a small change you want>: register the feature and write its spec."), and approve the spec on the dashboard. `cerne next` lists those steps plus the accept (`cerne feature accept <id>`), each ticked from the event log until the first accept. The first-week guide covers the rest in order: connecting each agent, the first feature, changing your mind, search and the wiki, the backlog and the daily routine: https://github.com/henriquesakata/cerne/blob/main/docs/first-week.md (`docs/first-week.md` in the repository).

## Q: Which files from cerne init do I commit? Do I commit the .claude folder?
Commit the four files `init` names at the root: `.cernerc`, `docs.lock`, `.gitattributes` and `.gitignore` (which now ignores `.docs/`, the generated projection). `init` also writes `.claude/` for Claude Code: commit `.claude/settings.json` and `.claude/hooks/` too, so a teammate's Claude Code gets the same hooks and `CERNE_ACTOR=agent`. `.claude/skills/` can stay out of git (add it to `.gitignore`): `cerne skill install` recreates it on each clone, and `cerne update` renews it with each release.

## Q: push or pull reports a conflict in a document. How do I resolve it? Why does push refuse an unreconciled conflict?
`cerne push` reports a conflict when the backend changed the same document since your copy of it: nothing is sent. Run `cerne pull`: it merges your unsent edit with the remote one line by line, and when the two touched different lines the document comes back with both and the next `cerne push` sends it. When they touched the same lines, pull keeps your version in `.docs/` and stashes the remote one under `.docs/.conflicts/<same path>`. It stashes instead of merging, even for different lines, when it cannot find the version both edits started from: in OKF mode, with no git binary on PATH, for a file whose line endings changed (CRLF), or when another push or command moved the snapshot past your copy. Fold the remote changes you want into your file and delete that stashed copy: pull keeps the copy and keeps reporting the conflict until then, and push refuses the document while the copy exists, because sending it would erase the remote edit. `cerne push --force` sends your version over the remote one and deletes the copy. A file inside a hidden folder of `.docs/` (`.obsidian/`, `.trash/`) is not a document: push ignores it.

## Q: Which section names do I use in an English project? Which language does the project document in, and which forms (Bar, CLARIFY, criterion N) do I write?
A project documents in one language, `en` or `pt-BR`, recorded in its backend; `cerne init` writes `en` unless `--docs-language pt-BR` is given. The session-start context carries a DOCS LANGUAGE line naming it and listing its section names and forms; without it, the headings of the stub you are filling tell you. Use only the forms of that language: in `en`, the spec sections are Problem, Goal and acceptance criteria, Design decisions, Design, Verification, Recommended execution (agent) and Out of scope, the bar line is `Bar:`, the open question is `[CLARIFY: specific question]` and an evidence citation is `criterion N`; in `pt-BR`, `Problema`, `Verificação`, `Barra:`, `[ESCLARECER: …]` and `critério N`. Reading is bilingual (lint and the gates accept either vocabulary), writing follows the project. The full table is in the authoring guide, `reference/language.md` (`cerne guide "documentation language"`).

## Q: Codex says permission denied or operation not permitted on every cerne command, or the network fails (pull, push, AI layer). How do I connect Codex so cerne works in its sandbox, and how do I open the network?
Codex runs commands in a sandbox that writes only the project, `/tmp` and `$TMPDIR`, and cerne keeps its cache and local backend in your home. `cerne hook install --provider codex` adds a `cerne` profile to the project's `.codex/config.toml` (`default_permissions = "cerne"`, extending `:workspace`) that opens both folders with `~/` paths, and keeps your own lines. The project's `default_permissions = "cerne"` replaces your own default profile inside this project; it extends `:workspace`, and `-s`/`-P` on the command line still win. When `default_permissions` is already set, the file is not valid TOML, or any folder is specific to this machine (`CERNE_CACHE_DIR`, `XDG_CACHE_HOME`, a local backend outside the home), it writes nothing to the project file and prints one snippet with every folder for `~/.codex/config.toml` plus `codex --add-dir <folder>`. Codex reads `.codex/` only in a trusted project: add `[projects."<project path>"]` with `trust_level = "trusted"` to `~/.codex/config.toml`. Check it inside Codex: `printenv CERNE_ACTOR` prints `agent` and `cerne next` runs with no permission error. What the sandbox cuts besides the folders is the network (`:workspace` has none): inside Codex, `cerne pull`/`cerne push` with a remote backend and the AI layer (`plan draft`, `result draft`, `ask`, `compile`, which call your subscription CLI and report `Not logged in`) fail, and cerne says the Codex sandbox may be cutting the network. `cerne hook install --provider codex --network` adds `[permissions.cerne.network]` with `enabled = true` to the profile (also to a project that already has the profile). It opens the whole network to the agent in this project: Codex has no domain list. That is why it is never the default and `cerne init` never suggests it. To turn it off, set `enabled = false` or delete the table in `.codex/config.toml`.

## Q: Cursor says operation not permitted on cerne's cache (repo.lock), or pull and push fail inside Cursor. How do I make cerne work inside the Cursor sandbox, open the network to the backend, and get the cerne MCP server in Cursor?
Cursor runs an agent command that is not on your allowlist (a chained `&&` command, a pipe) in a sandbox that writes only the workspace and `/tmp` and denies the network. In your own terminal (the agent cannot write `.cursor/*.json`), run `cerne hook install --provider cursor`: it adds cerne's cache folders and a local backend repository inside your home to `additionalReadwritePaths` in `.cursor/sandbox.json` (`~/` paths, your keys kept), and declares the read-only server `cerne mcp` in `.cursor/mcp.json`, the only project MCP file Cursor reads. The automatic refresh never writes either file. For `cerne pull`/`cerne push` with a remote backend, run `cerne hook install --provider cursor --network`: it adds only the backend's host to `networkPolicy.allow`, sets no `default`, and writes nothing when a `networkPolicy.deny` entry could match the host; a local backend opens nothing. Invalid JSON or a machine-specific folder (`CERNE_CACHE_DIR`, `XDG_CACHE_HOME`, a backend outside the home) writes nothing and prints the block for `~/.cursor/sandbox.json`. The AI layer (`plan draft`, `ask`, `compile`) needs your provider's hosts in `networkPolicy.allow`, added by hand.

## Q: Can I retag a closed feature, a superseded note or a dropped idea? Does a retag change its body or the stats?
Yes. Tags (`--facet`, `--component`) can be updated in any state: `cerne feature retag F-NNNN --facet <f> --component <c>` works on a done, rejected or superseded card too, and so do `cerne note retag`, `cerne decision retag`, `cerne runbook retag`, `cerne reference retag`, `cerne idea retag` and `cerne pending retag`. A retag changes only the tags of the entity you name, and only the axis you pass (`--facet ""` clears it); state, body, errata, links and lifecycle dates stay, the `<kind>.retagged` event goes to the log and the flow metrics of `cerne stats` do not move. A facet outside the closed set (infra, code, data, process, auth) is still refused. The body of a closed entity does not change this way: it changes only by `cerne note errata <id> "<text>"` (or the same verb of another kind).

## Q: Which component do I tag with? How do I avoid a near-duplicate component?
Pick one that exists: `cerne tags` lists every component in use with how many entities of each kind carry it (`cerne tags --json` too). A new component of the same root as an existing one (`test`, `tests`, `testing`) or a few characters from it is refused with the existing name to use; add `--force` only when it is a different thing (every command that writes a component takes it, the retags included). A genuinely new name is accepted with a `new component` notice on stderr. To read the notes of a group of components run `cerne note list --component a,b,c`: any of them, most matches first, with the gist and what matched; `cerne decision list --component a,b` and `cerne reference list --component a,b` take the same group. `cerne lint` reports single-use, same-root and note-only components as warnings.

## Q: How do I rename a tag everywhere? How do I rename or merge a component on every entity?
Run the dry run first: `cerne tags rename <from> <to> --dry-run` lists every entity that carries `<from>` (features, tasks, fixes, epics, notes, decisions, references, runbooks, pendings and ideas, in any state, closed ones included), each with its state and its components before and after, says whether `<to>` is a new component or a merge into one already in use (and on how many entities), and writes nothing. Then `cerne tags rename <from> <to>` writes it: one commit, one `<kind>.retagged` event per entity, only the components change. In a merge, an entity that already had `<to>` keeps it once. A new `<to>` near an existing component is refused like any new name; `--force` passes it. `--json` gives the same report. To fix one entity only, retag it: `cerne feature retag F-NNNN --component <list>` (or the same verb of another kind).

## Q: Where do I start a session? What do I run first, cerne next or .docs/CONTEXT.md?
Start with `cerne next`: the live features grouped by their next action, plus the lint debts. Then start a task from its package, `cerne context <id>` (next question). `.docs/CONTEXT.md` is the map of what is live (the features not yet done, the epics with a live child, active decisions and runbooks, work in progress) and of the components of the active notes; it stays within 16 KB and counts what it leaves out. Read it when you need the map, not first. `cerne brief` lists every entity, and `cerne feature list --state done` the done features.

## Q: How do I start a task? What does an agent read for one feature, without loading the whole project? What is the task package?
Run `cerne context <id>` (a feature, epic, task or bug): its document of the stage whole (the plan in development), its epic, and its neighbourhood in four rings: (a) what its documents and its epic's link by `[[id]]` or what informs them, the active notes and decisions with their body, since the author linked them; (b) active notes whose `edit:` trigger or cited file matches a path its spec or plan cites; (c) active notes sharing a component, the least used first; (d) up to five active notes the search index ranks for its title and problem. Every other item is an id, a title and its one-line gist. It closes with the counts of the decisions, references, runbooks and rejected or superseded proposals on its components, each with the command that lists them; read any item with `cerne show <id>`. `--budget N` (default 8000 estimated tokens) drops the items of rings (d), (c) and (b) first, then the ring (a) bodies, the longest first; only then it cuts what is left to id and title and drops ring (a) items, and the last line counts what left; the document is never cut. `--json` and the MCP tool `context` return the same. It reads the local clone and index as they are: no network, no model. `cerne feature start`, `cerne work start --ref` and `cerne handoff take` end with the index of the notes of rings (a) to (c) and this command, and a subagent of a session bound to a task gets them at its start. A note with no trigger and no link reaches an agent only through a shared component, a file both cite or a search: link it with `cerne note link <N-id> --informs <id>` or give it a trigger with `cerne note when`.

## Q: How do I link a decision to the feature or task it informs? What does decision link do?
At birth, `cerne decision new "<title>" --informs F-NNNN` (comma-separated ids of features, epics, tasks, bugs, decisions, runbooks, notes or ideas); later, `cerne decision link D-NNNN --informs F-NNNN`, and `--unlink F-NNNN` removes it. An unknown id is refused, the id may be in any case, and each change is a `decision.linked` or `decision.unlinked` event. `cerne show D-NNNN` lists what it informs. A linked active decision enters ring (a) of the task package, `cerne context F-NNNN`, with its body, as a note linked by `cerne note link N-NNNN --informs F-NNNN` does. A decision that only shares a component with the task stays a count with `cerne decision list --component <list>`.

## Q: How do I message the agent that opened, wrote or implemented a feature? Which session worked on a card, and how do I reach one whose work already closed?
The feature's page in `cerne ui` has an Agents panel: the sessions of this machine that opened the card, wrote its spec, plan or result (often three different agents), implemented it (`cerne feature start`), reviewed it as critic or judge, or worked on it through a W-. Each row shows the session's title as the Claude Code app shows it, its folder, branch, PR, last activity and the `cd <folder> && claude --resume <session>` command to copy. The panel's chat posts to the checked sessions only: each receives it at its next contact point (prompt, command, edit, session start, end of turn) even when its work already closed, until it answers or acks. A session waiting for you runs no hook and reads nothing until you open it: the thread says so and shows its resume command. Each row also has a button that opens the chat for that session alone, and a not-reached session's resume command starts it by reading the waiting message. As the addressed agent, answer with `cerne msg send --ref F-NNNN "<text>"` (the answer goes to the card's thread, not to the other agents; with no live work `--ref` may be omitted) or `cerne msg ack <seq>`. The panel exists only in the local `cerne ui`, never under `cerne serve`.

## Q: How do I turn on shell completion (Tab) for cerne in bash, zsh, fish or PowerShell?
`cerne completion <shell>` prints the script; INSTALL.md, section "Shell completion", has the block that turns it on in every new shell, writing only inside your home folder. bash (it needs the `bash-completion` package, version 2) saves it in `~/.local/share/bash-completion/completions/cerne`; zsh adds `source <(cerne completion zsh)` to `~/.zshrc`, after `compinit`; fish saves it in `~/.config/fish/completions/cerne.fish`; PowerShell adds `cerne completion powershell | Out-String | Invoke-Expression` to `$PROFILE`. The every-session paths in the command's own help (`/etc/bash_completion.d`, `${fpath[1]}`) usually need root. Then open a new shell: Tab completes cerne's commands and flags.

## Q: cerne room watch --once wakes me on the first message of a burst. How do I get the rest of the replies in the same turn?
It already waits for them: `--once` prints the first relevant event, then keeps printing what arrives until `--settle` passes with no new relevant event (default `1.5s`), and stops at most `5s` after the first event so a busy room cannot hold your turn. Your own echo is not printed but still advances the cursor. Raise it for slower agents (`cerne room watch <room> --once --settle 3s`); `--settle 0` exits on the first batch. A `close` event always ends the watch at once, printed, without waiting out the window. The window running out is a normal exit 0, not an error.

## Q: How do I speak in a war room without passing my session token on the command line? Where does room join keep the session, and the facilitator capability?
Never pass it on the command line: a `--session` or `--facilitator` value, or an inline `CERNE_ROOM_SESSION=<…>` prefix, shows in the process list while the command runs (an agent harness keeps each shell call's whole command line in the argv of its shell wrapper), in the shell history and in transcripts, and whoever reads it speaks as your nick or closes the room. In an agent session (`CERNE_SESSION` is set, exported by the SessionStart hook), `cerne room join <room> --nick <nick>` stores the session in a 0600 file of the cerne cache, one per room and agent session; then `cerne room say <room> "<message>"`, `cerne room watch <room> --once` and `cerne room request-decision <room> --title "<question>"` find it with no flag and no variable. In a human terminal nothing is stored: `export CERNE_ROOM_SESSION=<printed by join>` once, then the same commands. `--session` and `CERNE_ROOM_SESSION` still work: `--session` wins over everything, `--nick` takes that nick's stored session even when `CERNE_ROOM_SESSION` is set (an agent started from a shell that exported it inherits the variable), and the variable wins over a command without `--nick`. The facilitator capability that `cerne room open` prints is never stored, so no subagent of the opener's session holds the role: `export CERNE_ROOM_FACILITATOR=<printed by open>` in the shell that runs `cerne room pending <room>` or `cerne room close <room> --minutes <file>`. Those commands are short-lived, so in an agent harness the capability can still sit briefly in the shell wrapper's argv; that residual is accepted to keep the facilitator role apart from the participants. A subagent shares its parent's `CERNE_SESSION`, so join stores each nick of that agent session under its own name; with more than one in the room, pick yours with `cerne room say <room> "<message>" --nick <nick>` (a nick is not a secret), and a command without `--nick` refuses and lists the stored nicks instead of guessing. `cerne room facilitator handoff` and `reset` store nothing: the new capability is for the next bearer. It guards against accidental exposure, not against a process of the same user that reads the cache.

## Q: I can't close a war room: nobody has the facilitator capability. What now?
`cerne room close` needs the room's facilitator capability. `cerne room open` prints it once; a room opened in `cerne ui` keeps it in that browser, and "Transfer facilitation" removes it from there and shows the new one only once. When it is lost, a human runs `cerne room facilitator reset <room>`: it prints a new capability, every earlier one stops working, and the running `cerne ui` accepts it without a restart. An agent is refused (it is a human act), so ask the human. Then `export CERNE_ROOM_FACILITATOR=<new>` and close with `cerne room close <room> --minutes <file>`.

## Q: How do I leave a war room so my session stops working? Does closing the tab leave?
`cerne room leave <room>` revokes your participant capability on the server (it finds your session the same way as `say`, so pass `--nick <nick>` when this agent session keeps several, and on success it drops that session from the stored file): from then on it stops working for `say`, `watch`, `propose` and `request-decision`, a `leave` event goes into the transcript, and you drop out of the room's active participants while the minutes still count you among those who took part. In `cerne ui`, the room's Leave button does the same and only then forgets the session in that browser. Closing a terminal, a tab or the browser does not leave: a reload picks the same session up again. To come back, `cerne room join <room> --nick <nick>` mints a new capability; the nick is free again. To only follow a room, `cerne room read <room>` needs no session. Leaving never touches the facilitator capability.

## Q: The facilitator asked me to write the war room minutes. Where do I put them, and how does the room close with them?
In the room, not in a loose file: `cerne room minutes draft <room> --minutes <file>` (or `-` for stdin, or an inline JSON object; `cerne room minutes template` prints a blank one) validates the minutes, with `conclusion` and `rationale` required, and saves them as the room's current draft. A refused draft saves nothing. The room stays open, a `minutes_draft` event tells everyone watching, and a later draft replaces the earlier one. It saves as your session, found the same way as for `say` (pass `--nick <nick>` when this agent session keeps several), or as the facilitator, with `CERNE_ROOM_FACILITATOR` exported when no session is found. Read the current draft, with its author and time, with `cerne room minutes show <room> --draft`. Only the facilitator closes with it: `cerne room close <room> --use-draft`, in place of `--minutes`, and still refused while items are open unless `--allow-open-items`. It closes with the draft it reads and prints that draft's author and time; a draft saved in between refuses the close, so review the new one and run it again. In `cerne ui` every viewer sees the draft, and the facilitator closes with it in one click or loads it into the close form to edit first. The draft ends with the room. The nick `facilitator` is reserved for the facilitator's drafts.

## Q: Which war room participants are listening right now, and who is idle?
`cerne room list` prints each open room as `<N> participant(s) (<L> listening)`: N counts the active participants, so whoever left drops out, and L those whose session is waiting for events right now. An agent that runs `cerne room watch <room> --once` is listening while the command waits and idle while it works between turns. In `cerne ui`, the room's roster marks each active participant as listening or idle, with the last activity: join, resume, say, propose, request-decision, a minutes draft or a read with the session. A browser tab that joined the room reads with its session, so it listens while it is open; reading without a session, as `cerne room read <room>` or an observing tab does, does not count. Presence lives in the running `cerne ui` only: it is not in the transcript, starts empty after a restart, and a closed room shows none.

## Q: How do I create a task, epic or feature with its capability in one command? How do I link several cards to a capability at once? Why does `cerne next` cut the debts list?
Pass `--capability C-0001` (a comma-separated list is fine) to `cerne feature new`, `cerne epic new` or `cerne task new`: the card is born already linked, in the same single commit as its creation. Every id is checked first, and an unknown or retired one creates nothing, so a retry hits no duplicate guard. To link existing cards in bulk, give `cerne feature capability` a comma-separated first argument, for example `cerne feature capability T-0019,T-0020,T-0021 C-0006` (`--clear` works too): one commit, aborted whole if any id is wrong. `cerne next` shows at most 5 items per lint rule under DEBTS (each rule header keeps its total) and 10 open pendings, ending the cut list with `… and N more`; `cerne next --all` lifts both caps in the text output, `cerne next --json` is never cut, and `cerne lint` always lists everything.
