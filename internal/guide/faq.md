## Q: What is cerne? What does cerne do? How do I start using cerne?
cerne is an engineering workflow for software built with AI agents, in one local binary: a CLI and a web UI (`cerne ui`). What it does: keep the living documentation, separating the current state from history. The lifecycle of features, decisions and references is structured data in a git backend; `cerne pull` writes only the current state to a gitignored `.docs/` folder that agents read. It does not run in the cloud. Start with `cerne init` at the project root, or try a sample with `cerne demo`; `cerne guide` lists every command.

## Q: A command fails with "cache clone belongs to another backend". What now?
Two projects on this machine share one `project_id`, and the local cache is keyed by that id alone, so the clone in the cache is the other project's. cerne refuses to read or write through it, and never deletes it (the cache also holds rooms and messages). Give this project its own cache with `CERNE_CACHE_DIR=<dir>`, or a distinct `project_id` in its `.cernerc`. `cerne demo` already picks `taskflow-2`, `taskflow-3`… when `taskflow` is taken.

## Q: A command fails with "the folder does not accept writes" (permission denied on the cache, or search fails). What now?
The cache folder, or the local backend folder, is read-only for this process, typically an agent sandbox (Codex, for one) that only lets the project folder and /tmp be written. Nothing is corrupt and nothing needs deleting. Make the folders named in the message writable (the cache, `CERNE_CACHE_DIR` when set; for a local backend, its data folder, `CERNE_DATA_DIR` when set), or point `CERNE_CACHE_DIR` at a writable path, then re-run.

## Q: Which command do I run first? I just installed cerne.
Read the top-level help (run cerne with no arguments): the first section, "Start here", holds the on-ramp. `cerne init` sets up a project (or `cerne demo` creates a sample one to explore), `cerne ui` opens the dashboard, `cerne import` brings in an existing documentation tree, and `cerne guide "<what you want to do>"` answers any later question. The other sections group the rest by journey: read the state, author and move the work, sync with the backend, agents and coordination, administration.

## Q: How do I close a feature? One command or two?
Fill the result, `cerne push`, then `cerne feature complete <F-id>`: it moves the feature to implemented and stamps its token cost (`## Custo`) in the same command, the same stamp as `cerne cost <F-id> --stamp`. If the transition refuses, nothing is stamped. If the stamp cannot be made it prints `warning: cost not stamped: …` and still exits 0, because the feature is already implemented: when no session on this machine is bound to it, run `cerne cost <F-id> --stamp` from the machine that ran the work. `--no-stamp` skips the stamp. The output ends with one Next step block: the human `cerne feature accept <F-id>` and, when the feature has a PR link, the delivery line. Marking the PR ready for review is not done by cerne. Run the complete as soon as the PR is open: human review starts when the card is in Ready, so do not wait for CI or the merge.

## Q: I asked a human to approve or accept. How does the agent know when they did?
Leave `cerne feature wait <F-id> --for approved` (after the complete, `--for done`) running in the background, then stop. When the human acts, it exits with one line — the transition, who made it and when, and the next step — and a harness that wakes the session when a background command ends (interactive Claude Code does) brings the agent back without anyone typing. Exit 2 means the state can no longer be reached (rejected, superseded), exit 3 the `--timeout` (24h by default; `0` checks once). It only fetches the backend clone, never pulls, so `.docs/` is untouched. In a harness without background commands, just stop: the human tells the agent. The gate stays human: the agent never runs the approve or the accept itself.

## Q: How do I change a project setting from the CLI?
Use `cerne settings set <key> <value> --scope project`. `--scope` is required: `project` writes `.cernerc`, `host` writes the user's `settings.toml`. See every key, its value and where it comes from with `cerne settings list`, read one with `cerne settings get <key>`, remove an override with `cerne settings unset <key> --scope project`. Owner-only keys such as `gates.gauntlet` refuse an agent (`CERNE_ACTOR=agent`): ask the owner.

## Q: Where is the cerne UI API? Which URL does the dashboard call?
`cerne ui` serves every project from one process, so each route is under `/api/projects/<pid>/…`, where `<pid>` is the project id of `.cernerc`. `GET /api/projects` lists the registered ids. A bare `/api/<route>` is not the UI API. The default port is 7717 (`cerne ui --port`).

## Q: Why does a request to the cerne ui API answer 403?
`cerne ui` answers only on this machine. Every request, reads included, needs a loopback `Host` (`127.0.0.1`, `localhost` or `[::1]`, any port), and a write (any method but GET and HEAD) also needs an `Origin`, when the request sends one, that names that same host. A domain name rebound to 127.0.0.1 gets 403 and reads or writes nothing; so does a forwarded hostname (a Codespaces port, a reverse proxy): open the UI at the loopback address. A page on another site gets 403 on a write. Call `http://127.0.0.1:7717/api/projects/<pid>/…`: the CLI and curl send no `Origin` and pass. Some routes also check the body type (JSON, or markdown for the Vault's saves). The remote `cerne serve` does not apply this check.

## Q: Can the UI edit a note, decision or runbook? Why did a save answer 409, 422, 400, 403 or 413?
Yes: the Vault (`#/vault` in `cerne ui`) edits the open document in place — a live feature's spec, plan or result, and an active decision, note or runbook. The save goes through the same core as the CLI, as a human, with a commit and a push. Each read carries the sha256 of the document (`content_hash`, or `docs_hash` per feature document) and the editor sends it back as `If-Match` on `PUT /api/projects/<pid>/notes/<id>/content` (also `decisions/`, `runbooks/` and `features/<id>/docs/<doc>`). A 409 means the backend document changed since it was loaded: nothing was written, and the body carries the current `content` and its `content_hash`. A superseded or retired entity answers 422 `entity is not live — append an errata instead`: history takes `cerne note errata` (or `cerne decision errata`, `cerne runbook errata`). A 400 names a `cerne_id` in the frontmatter that is not the entity's own: `cerne push` routes a document by it, so the save refuses it. A 403 means the write did not come from `cerne ui` on this machine (it needs a loopback host and a same-origin markdown request). A 413 means the body is over 4 MiB.

## Q: How is the before and after of a process marker dated?
A process marker is a decision with facet `process` and component `metric`. `cerne stats --process` judges the 28 days before and after it, and the date it uses is when the decision was created (`cerne decision new`), not when the change shipped. Create the marker decision the day the change goes live, or the window is wrong.

## Q: How does the judge's cost reach the feature? Why is the judge missing from by_role?
The Gauntlet's critic and judge run no cerne command, but `cerne cost <feature-id>` and `cerne cost --stamp` recognise them from their transcripts: a judge ends its last reply in the verdict line (`VEREDITO: A|B|EMPATE`) or was asked for it, and a critic is a `code-reviewer` or read the criteria and diff fences of the Gauntlet package, in its first message or in a file it read. Nothing to run by hand. A role bound with `cerne cost attribute <agent-id> <feature-id> --role judge` still wins over that recognition. For Gauntlets already done, `cerne cost backfill-roles` reports the roles it can recover (add `--apply` to record them and complete each anchor; a done feature gets an erratum with the `## Custo` block). The By role block of `cerne cost <feature-id>` lists builder, critic, judge, other and main.

## Q: A subagent ran feature start. Why does the cost stamp say nothing to stamp?
The bind hook binds the subagent that runs `cerne feature start <F-id>` under its own key, so `cerne feature complete <F-id>` and `cerne cost <F-id> --stamp` count its tokens with no extra step, even when the output was piped or redirected (`cerne feature start T-0005 2>&1 | tail -5`): without the transition line in the output, the hook checks that the feature is now in_development. A start the hook never saw (an older cerne, hooks not installed, another machine) leaves the subagent unbound: run `cerne cost attribute <agent-id> <F-id> --session <session-id>`, then `cerne cost <F-id> --stamp`. The agent id is the `agent-<agent-id>.jsonl` file under the session's `subagents/` folder.

## Q: How do I get the id of an idea I just created?
`cerne idea new <title>` prints the id on its first line (`I-0007 created (active) — …`); the optional body comes from `--file` or stdin. Lost it? `cerne idea list` shows ids, newest first (`--state resolved|dropped|promoted|all`, `--component <c>`). Turn it into a candidate with `cerne idea promote <id>`, point it at a feature that is already live with `cerne idea link <id> <F-id>` (`cerne idea unlink <id>` undoes it), close one something else already delivered with `cerne idea resolve <id>`, or drop it with `cerne idea drop <id> --reason "<why>"`. A promoted or linked idea follows its feature: the accept resolves it, a reject reopens it. Ideas stored before title and body: `cerne idea migrate --dry-run`, then `cerne idea migrate`.

## Q: cerne next shows no cost stamp line for a feature I worked on in Codex or another harness. Is it stuck?
No. `cerne cost` reads Claude Code transcripts only, so a session bound under another harness cannot be stamped, and `cerne next` does not list it under FINISH DELIVERY (that section holds only runnable commands: `cerne cost <F-id> --stamp` when the stamp would run, `cerne feature deliver <F-id> --mr <url>` when no PR link is recorded). With the delivery link in, the feature moves to WAITING FOR HUMAN ACCEPT. An unreadable cost ledger still shows as `cost check failed: …`.

## Q: How do I turn the Gauntlet off? Light mode without the bar and the judge.
The Gauntlet is the setting `gates.gauntlet` (`on` or `off`). The owner flips it in the Settings screen of `cerne ui` or with `cerne settings set gates.gauntlet off --scope project`; the command refuses an agent. With it off, `cerne feature approve` takes a spec with no `Barra:` line and `cerne feature complete` takes a result with no `## Gauntlet` section, but each criterion still needs its evidence. `cerne status` prints `Gauntlet: off (light mode)`. An agent never switches it to get past a gate.

## Q: How do I hand my work to another agent? Pass the baton.
Record the handoff with `cerne work handoff <W-id> --next "<next step>" --file brief.md --evidence <ref>,<ref>`; it prints an `HO-` code. Pass only that code. The receiver runs `cerne handoff take <HO-id>`, which opens its own work, closes yours and prints the brief. Review pending ones with `cerne handoff list`, withdraw with `cerne handoff cancel <HO-id>`. Add `--if "<condition> → <action>"` once per contingency.

## Q: How do I register an external source, an article, a link or a spec?
`cerne reference new "<title>" --url <url> --informs F-0001,D-0002 --file summary.md` (or pipe the summary on stdin). The reference is marked external, its text is indexed so `cerne ask` cites it, and `--informs` links it to the entities it motivated. A bare URL in a decision or feature makes `cerne lint` report `unregistered-source`. A live reference with the same URL is refused unless `--force`.

## Q: Why does cerne ui serve an old screen or a 404 after I reinstalled cerne?
A `cerne ui` process keeps serving the embedded UI and API of the binary it started with. The panel notices when its command resolves to another binary on disk (an upgrade through Homebrew or the install script, or a new local build) and shows a notice with a Restart the panel button: it restarts into the new binary on the same port, keeps the other registered projects and reloads the open tabs. A `cerne ui` of the installed binary run in another project restarts the panel by itself. A panel started by a release from before this notice has neither: stop that process (it listens on port 7717) and start `cerne ui` again.

## Q: How do I start working on a feature and finish it?
`cerne feature new "<title>"` registers the candidate, `cerne pull` materializes `.docs/`, fill the spec and plan, `cerne push`, then the human runs `cerne feature approve <F-id>`. The builder runs `cerne feature start <F-id>`, writes the result, `cerne push`, then `cerne feature complete <F-id>`. `cerne feature accept <F-id>` is the human validation step that makes it done.

## Q: Do cerne's hooks work in Cursor? What does the third-party setting give me?
Yes, through Cursor's import of the project's `.claude` hooks, the setting "Include Third-Party Plugins, Skills, and Other Configs" (Cursor Settings, Agents, Third-Party Imports; on by default). With it on, the same hooks run in Cursor: the registration rules and live board at session start, the work gate, the session binding after `cerne work start` or `cerne feature start`, the provenance reminder, and the end-of-turn closeout, which Cursor submits as a follow-up message. Cursor's agent shells carry `CURSOR_AGENT=1`, so `cerne feature approve` and `cerne feature accept` refuse a Cursor agent as they refuse a Claude Code one. With the setting off, only `.cursor/rules/cerne.mdc` and the session-start board from `.cursor/hooks.json` (`cerne hook install --provider cursor`) reach Cursor.

## Q: How do I connect codex, cursor or gemini to my project? Which agents did cerne init connect?
`cerne init` connects Claude Code (guide and hooks) and delivers the authoring guide to every other agent whose folder (`.cursor/`, `.codex/`, `.gemini/`) already exists in the project; it ends with `Agents connected: claude.` and `To connect ...` naming the others. To connect them, run `cerne hook install --provider <name>` (creates the agent's folder and hooks), then `cerne skill install` (the authoring guide). `cerne init --verbose` lists every installed file.

## Q: How do I make GitHub Copilot work with cerne? Which of cerne's hooks does it get?
Run `cerne hook install --provider copilot` and `cerne skill install` (Copilot is also picked up automatically when the project has `.github/copilot-instructions.md`, `.github/hooks/`, `.github/skills/` or `.github/agents/`). They write `.github/hooks/cerne.json` (session-start board, work gate, session binding, provenance reminder, stop closeout), the authoring skill under `.github/skills/cerne-authoring/`, the rules in `.github/instructions/cerne.instructions.md` (the project's own `copilot-instructions.md` is not touched) and the read-only `cerne` server in the root `.mcp.json`. In `copilot -p` the repository hooks only load in a trusted folder (`--trust-folder`). The Copilot cloud agent does not read `.mcp.json`: paste the block the install prints into the repository settings and install the cerne binary in its environment. Degraded rows and what is verified: see the next question.

## Q: What is degraded or unverified when cerne runs on GitHub Copilot?
Copilot degradations (docs/provider-parity.md): Handoff code through compaction (preCompact is notification-only); Document author (CERNE_PROVIDER, F-0375) (reaches the hooks, not the bash shell); Subagents with live board (no subagent hook); Notes matching the prompt (B-0020) (no verified prompt-submit event wired); Stop closeout (the block decision was never exercised live, treat it as unverified); Double execution with the .claude hooks (Copilot CLI runs both sets and ignores the Claude-format output, so only side effects repeat). Copilot's bash shell is marked `COPILOT_CLI=1`, so `cerne feature approve` and `cerne feature accept` refuse it as they refuse Claude Code, verified on Copilot CLI 1.0.112 only; VS Code agent mode and the cloud agent are unverified. `.github/hooks/cerne.json` belongs to cerne and is rewritten whole when it differs (keep team hooks in their own file there); a corrupt `cerne.json` or `.mcp.json` is left untouched and reported as skipped.

## Q: Does each task of an epic need its own approve and accept? Which bar does a task declare?
No. Decompose an approved epic with `cerne task new "<step>" --parent E-NNNN --file spec.md`: the task is born approved. The human's `cerne feature approve E-NNNN` also approves every candidate child that passes `cerne feature approve <id> --check`, and `cerne feature accept E-NNNN` also accepts every implemented task, so an epic costs two human acts whatever the number of tasks; an F- child keeps its own accept. Each task declares its own bar in its spec: a named bar (its result records the round), `Barra: não aplicável (…)`, `Barra: dispensada por decisão humana (…)`, or `Barra: herdada de E-NNNN` (EN: `Bar: inherited from E-NNNN`), which needs a named bar on the parent and puts the round in the parent's result. `cerne feature start T-NNNN` refuses a spec with no valid bar.

## Q: What do I do right after feature new? What is the Next step block?
`cerne feature new`, `cerne epic new` and `cerne idea promote` end with a Next step block that lists what the candidate still lacks, in order: the real spec (when it was seeded from `--context`), the tags, the capability (when the project curates a taxonomy), then `cerne feature approve <F-id> --check`, and last the human approve, where an agent stops without implementing. `cerne feature start` ends with its own block: consult the active notes with `cerne note list` before the code, keep `plan.md` and `result.md` current, `cerne sync` at each milestone. The blocks are the command's own output, so every harness (Claude Code, Cursor, Codex, Gemini) gets the same text, with or without hooks.

## Q: How do I read the project state without loading everything?
`cerne brief` is the cheapest map (id, state, title). `cerne status --active` shows only active work, `cerne next` the next action per feature plus documentation debts. Read one entity with `cerne show <id>`, search by subject with `cerne search "<query>"`.

## Q: Where do the learnings from a result go? How do I reuse what a past agent learned?
A result's learnings are history and do not reach the next agent by themselves. `cerne feature complete` lists them. A durable one becomes a note with `cerne note new "<title>" --informs <F-id> --component <topic>`; first find a note that already covers it (`cerne note list --path <file>` or `cerne search "<terms>"`): complement it with `cerne note errata <N-old> ...`, or if it contradicts, replace it with `cerne note supersede <N-old> --by <N-new> --reason "..."`; none durable: `cerne feature learnings --skip <F-id>`. `cerne feature learnings` lists, read-only, the past features nobody triaged yet concluded since 2026-11-13 and counts the older ones apart; `--since 2026-01-01` lists them, `--feature F-NNNN` shows one.

## Q: What can cerne do? Which features exist?
Run `cerne guide` with no question: it prints the catalog of every command, grouped by area, straight from the command tree, so it is never stale. Then `cerne guide "<feature>"` (for example `cerne guide "gauntlet"` or `cerne guide "room"`) returns how to use it: the reference file of that area and the command help. `cerne guide --topics` lists the topics; a command name alone (`cerne guide "room"`) brings its help. The skill's `reference/` folder holds the same detail for agents that read files.

## Q: A human asked me to register this demand. How do I record who asked? What is the origin of a card?
Every new feature, epic or task stores `origin`: `agent` when your session runs with `CERNE_ACTOR=agent`, `human` otherwise. When the human asked and you only ran the command, pass their words: `cerne feature new "<title>" --context "..." --on-behalf "<quote of the human's request>"` (also on `cerne epic new` and `cerne task new`). That records origin `human` and the quote on the creation event; a blank quote is refused. Read it with `cerne show <id>` and filter with `cerne feature list --origin human|agent`. Cards created before the field have no origin.

## Q: A human reported a bug or a fix. Do I open a feature? How do I report a bug with cerne?
No feature: use a bug report. `cerne bug new "<what breaks>" --context "<what happens, where>" --steps "<numbered steps>" --expected "<should happen × what happened>" --on-behalf "<the human's words>"` mints a `B-` card with a three-section spec (Context, Steps to reproduce, Expected × actual; each filled by its flag) and the regression-test bar already filled. A human origin means the report is the approval: the card is born `approved`, so run `cerne feature start B-NNNN` right away, no plan and no approve. Add `--fixes F-NNNN` to link the delivered feature and inherit its tags. A bug you found yourself (no `--on-behalf`) is born `candidate`: ask a human to run `cerne feature approve B-NNNN`. Completing needs a real `result.md` and accept stays human. A person using the UI opens "Reportar correção" (`#/bug`, linked on the Manage page).

## Q: How do I update cerne? I updated the cerne binary but the project still has the old skill or hooks. How do they catch up?
Run `cerne update` inside the project. It updates the binary the way it was installed: Homebrew upgrades it; a script or hand install downloads the latest release, checks it against `SHA256SUMS` and swaps it in place. Then the new binary renews the hooks and the guide of the agents already connected, the same as `cerne hook install` plus `cerne skill install`, and connects no new agent. It closes with one line per part (binary, hooks, guide): updated, up to date, or not done with the reason and the command; the exit code is 0 only when nothing was left not done. A local build, a `go install` or a folder you cannot write keeps its binary and names the command. An agent can run it too, but never replaces the binary: that part is the human's, in their own terminal. `cerne update --check` lists what is out of date, writing nothing and using no network. On a version without the command, update the binary first with `brew upgrade henriquesakata/tap/cerne` or the install script.

The canonical skills (`cerne-authoring`, `cerne-self-learning`) and the managed hook scripts are embedded in the binary, so a new binary alone changes nothing on disk. While the project's files are older than the binary, `cerne next` opens with a line asking for `cerne update`, and so does the session-start hook. With `sync_skills = true` in `.cernerc`, `cerne pull` and the session-start hook rewrite the stale canonical skills by themselves. Hook scripts are never rewritten at session start, because they may be versioned in the project's git: review the diff after `cerne update`, which does not keep local edits to managed hooks. `cerne harness` shows the divergence per item.

## Q: Is someone already on this? Has a work already covered it?
Run `cerne search --works "<subject>"`: it lists only the matching works (id, state, actor, title; active first, up to 50), found by title, closing note, handoff and decision log. Words match as prefixes ("rota" finds "rotação"), all words first and any word when none has them all. The plain `cerne search "<subject>"` shows the same as a `Works:` group after its usual results, capped at 5 with a line saying how many more match. `--json` carries `works` and `works_total`. Active works are in progress now; done ones tell you who already covered it (`cerne show <W-id>` for the detail). If the first line says the search index was last synced long ago, `cerne pull` first: works written on other machines may be missing.

## Q: Who is working on what at the start of a session? Is the in-progress board stale?
The session-start hook (`cerne hook channel --point session-start`) prints the in-progress board read from the shared clone, not from the checkout's `.docs/CONTEXT.md`: the same active work, idle-work line and pending handoffs as the "In progress" section of `CONTEXT.md`, or one `- no active work` line. If the clone was last fetched more than 24 h ago it adds one line saying so; run `cerne pull` to refresh. `cerne work list` shows the same state on demand. The subagent point prints no board (it inherits the parent's context).

## Q: How do I check a draft spec before registering it? What does the chat's "Pedir correção" button do?
`cerne spec check --file <draft.md>` (or the body on stdin) lints a spec body without writing anything: the template sections that are missing, the Gauntlet bar line when absent or malformed (skipped in light mode) and open clarifications, which are warnings only. It exits 1 on an error and 0 otherwise; `--json` prints the same list. It is the check `cerne feature approve --check` and the `incomplete-doc` lint run. The Backlog chat runs it on every proposal block at the end of a turn and lists the issues on the proposal card; "Pedir correção" sends them back to the agent as your next message, and nothing is corrected behind your back.

## Q: cerne feature approve says "human gate", but I am the human. What now?
The command ran in a shell cerne reads as an agent's: `CERNE_ACTOR=agent` (stamped by `cerne hook install`), or, with no `CERNE_ACTOR`, the shell marker of Claude Code (`CLAUDECODE=1`), Cursor (`CURSOR_AGENT=1`), Copilot CLI (`COPILOT_CLI=1`) or Codex (`CODEX_THREAD_ID`, any non-empty value). The same refusal stops `cerne feature accept`, a revert and the human-only settings such as `gates.gauntlet`. Run the command in your own terminal, or declare yourself with the prefix: `CERNE_ACTOR=human cerne feature approve <id>`. A non-empty `CERNE_ACTOR` always wins over the markers. An agent never sets it: the gate exists so that an agent does not approve its own spec.

## Q: Why does a work, event or handoff author look like m-1a2b3c4d instead of my login?
cerne never records or shows a login or machine name as an author. `cerne work start` records `m-<8hex>` (the machine pseudonym: the first 8 hex of the SHA-256 of the lowercased `<user>@<host>`), or `agent:m-<8hex>` when `CERNE_ACTOR=agent`, or with no `CERNE_ACTOR` in a Claude Code, Cursor, Copilot CLI or Codex shell (`CLAUDECODE=1`, `CURSOR_AGENT=1`, `COPILOT_CLI=1`, `CODEX_THREAD_ID`, any non-empty value). A value with `@` given to `--agent` or `CERNE_ACTOR` is recorded as its pseudonym, and a value without `@` stays as it is. Records written before this rule keep their old text in the backend but are read as the pseudonym, so they still count as this machine's. `cerne work list` writes `session: on another machine or user (m-<8hex>)` for an active work of another pseudonym.

## Q: A new git worktree has no .docs/. How does an agent get the projection?
`.docs/` is gitignored, so a fresh worktree of a project that has its own `.cernerc` starts without it. The SessionStart hook (`cerne hook session-context`, every provider) builds `.docs/` itself from the local backend clone when `.docs/CONTEXT.md` is missing. It never contacts the backend and never resets the clone, so unpushed local state is safe; the context then carries one line saying the projection may be stale and that `cerne pull` refreshes it. If there is no clone yet, or the backend lock stays busy for a few seconds, the session still starts and the line says to run `cerne pull`. A worktree without its own `.cernerc` resolves to the main checkout (B-0016) and reads that checkout's `.docs/`, so nothing is built there.

## Q: I sent a message on the project channel and the UI says not delivered. When does an agent get it? Why does nobody answer?
A channel message reaches a session only at a contact point: session start, a subagent's start, the user's next prompt to that session, before each shell command and each Edit/Write (after the tool on Cursor, Gemini and Copilot), and the session's own `cerne next`, `cerne status --active` or `cerne msg read`. "Not delivered" means no live session of that work has passed one since the message was posted: an idle session gets it at its next prompt or tool call, and a work with no session on this machine is not waited for. A message the human sends is addressed to every session with live work: it comes back at each contact point, with the line telling the agent to answer with `cerne msg send "<text>"` or `cerne msg ack <seq>`, until it does. `cerne msg read` shows each message's state per work (not_delivered, delivered, answered). `hooks.prompt_notes` and `hooks.notes_on_bash` turn off only the notes, never the channel.

## Q: How do I turn off the note reminder the agent gets when I send a prompt?
Set `hooks.prompt_notes` to false: `cerne settings set hooks.prompt_notes false --scope project`. It is on by default. The UserPromptSubmit hook (cerne-prompt-notes.sh, installed by `cerne hook install`, Claude Code only) matches the prompt against the titles of active notes and runbooks in the local index and injects up to 3 `id — title` lines, once per session per id; read one with `cerne show <id>`. It never pulls or reindexes, so a stale index shows stale titles until the next `cerne pull`. The same hook also delivers the project channel's pending messages; turning the notes off leaves the channel on.

## Q: Do I have to repeat the title on the command line when the body already starts with a heading?
No. The `new` commands of notes, decisions, runbooks, references, features and bugs (`cerne note new` and its siblings) take the title from the body's first `# ` heading (after any frontmatter) when no title argument is given, from `--file` or piped stdin: `cerne note new --file nota.md`. A title argument, when given, still wins. The heading stays in the stored body, so the document shows it once. With no argument and no heading as the first line (a `# ` inside a code block or after other content does not count) the command refuses with "give a title or start the body with a `# ` heading"; a `--context`-only feature or bug still needs the title argument.

## Q: cerne runs gh or glab for another host and my GITLAB_TOKEN or GH_ENTERPRISE_TOKEN is not used. Why?
The committed `.cernerc` names the host (a `mirror.trackers` url, the `delivery.commit_url`), and gh and glab would send a token variable to whatever host they are pointed at, so cerne passes each one only to the host it belongs to. `GH_TOKEN` and `GITHUB_TOKEN` go only to github.com. `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` go only to the host in `GH_HOST`. `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN` and `OAUTH_TOKEN` go only to the host in `GITLAB_HOST`, else `GL_HOST`, else gitlab.com. Host names compare without case, scheme or port. Any other host gets the CLI's own login: run `gh auth login --hostname <host>` or `glab auth login --hostname <host>`, or set the host variable to that host, then run `cerne mirror sync` again.

## Q: How do I mirror cards to GitHub, GitLab, Gitea, Jira or Trello? Which credential does each tracker use?
A human adds the tracker to `mirror.trackers` (name, kind, url, label) and turns on `mirror.enabled` in the Settings screen of `cerne ui`; `cerne feature mirror <id> --title <title> --summary <summary>` then publishes a card, and `cerne mirror sync` keeps its issue in step. The url and the credential of each kind (no credential goes in `.cernerc`):
- `github`: `https://<host>/<owner>/<repo>`; the gh login, `gh auth login --hostname <host>`.
- `gitlab`: `https://<host>/<group>/<project>`; the glab login, `glab auth login --hostname <host>`.
- `gitea`: `https://<host>/<owner>/<repo>`; an access token in git credential for the host.
- `jira`: `https://<site>/browse/<PROJECT KEY>`; git credential for the site: the account e-mail and an API token on Cloud, a personal access token on Data Center.
- `trello`: `https://trello.com/b/<boardId>/<slug>`; git credential for `api.trello.com`: the API key as the username, the token as the password.
Store one with `printf 'protocol=https\nhost=<host>\nusername=<user>\npassword=<token>\n\n' | git credential approve`.

## Q: What does cerne next show on a new project? What are the first steps?
Until the first feature is accepted, `cerne next` opens with a FIRST STEPS block: ask your agent for a feature, approve its spec (`cerne ui` or `cerne feature approve <id>`), accept the delivery (`cerne feature accept <id>`). Each step is ticked from the project event log, nothing is stored, and the block links the first-week guide. The usual sections stay below it; after the first accept the block is gone.

## Q: What does cerne import tell me when it finishes, and can imported features start as done?
After `cerne import --yes` (and `cerne import --agent --ingest --yes`) the closing lists what came in by kind and by state, then two next steps: a `cerne search` over a word from the imported titles and the request to hand your agent for the first feature, plus the address of the first-week guide. A feature imported as delivered (a case with a result, or a status line saying it shipped) enters as `implemented`, waiting for your accept. Pass `--delivered-state done` to have it enter as `done` instead; `--delivered-state implemented` is the default. On a terminal, a dry-run import that finds delivered features and got no `--delivered-state` asks once which state to use and prints the flag to add when you apply; with `--yes` or with the flag given, it never asks. Without a terminal (an agent or a script) the dry-run does not ask: it prints `N delivered feature(s) will enter as implemented; add --delivered-state done to enter them as done.` The import writes only `<kind>.imported` events, never an approval or an accept, so the first steps in `cerne next` stay unchecked.

## Q: What do I do after installing cerne? What comes after init?
Run `cerne init` at the project root (or `cerne import --agent` when it already has docs), then follow the first steps it prints: open the dashboard (`cerne ui`), ask your agent for a small feature ("Use cerne to plan <a small change you want>: register the feature and write its spec."), and approve the spec on the dashboard. `cerne next` lists those steps plus the accept (`cerne feature accept <id>`), each ticked from the event log until the first accept. The first-week guide covers the rest in order: connecting each agent, the first feature, changing your mind, search and the wiki, the backlog and the daily routine: https://github.com/henriquesakata/cerne/blob/main/docs/first-week.md (`docs/first-week.md` in the repository).

## Q: push or pull reports a conflict in a document. How do I resolve it? Why does push refuse an unreconciled conflict?
`cerne push` reports a conflict when the backend changed the same document since your copy of it: nothing is sent. Run `cerne pull`: it merges your unsent edit with the remote one line by line, and when the two touched different lines the document comes back with both and the next `cerne push` sends it. When they touched the same lines, pull keeps your version in `.docs/` and stashes the remote one under `.docs/.conflicts/<same path>`. It stashes instead of merging, even for different lines, when it cannot find the version both edits started from: in OKF mode, with no git binary on PATH, for a file whose line endings changed (CRLF), or when another push or command moved the snapshot past your copy. Fold the remote changes you want into your file and delete that stashed copy: pull keeps the copy and keeps reporting the conflict until then, and push refuses the document while the copy exists, because sending it would erase the remote edit. `cerne push --force` sends your version over the remote one and deletes the copy. A file inside a hidden folder of `.docs/` (`.obsidian/`, `.trash/`) is not a document: push ignores it.

## Q: Which section names do I use in an English project? Which language does the project document in, and which forms (Bar, CLARIFY, criterion N) do I write?
A project documents in one language, `en` or `pt-BR`, recorded in its backend; `cerne init` writes `en` unless `--docs-language pt-BR` is given. The session-start context carries a DOCS LANGUAGE line naming it and listing its section names and forms; without it, the headings of the stub you are filling tell you. Use only the forms of that language: in `en`, the spec sections are Problem, Goal and acceptance criteria, Design decisions, Design, Verification, Recommended execution (agent) and Out of scope, the bar line is `Bar:`, the open question is `[CLARIFY: specific question]` and an evidence citation is `criterion N`; in `pt-BR`, `Problema`, `Verificação`, `Barra:`, `[ESCLARECER: …]` and `critério N`. Reading is bilingual (lint and the gates accept either vocabulary), writing follows the project. The full table is in the authoring guide, `reference/language.md` (`cerne guide "documentation language"`).
